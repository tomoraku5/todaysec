## 1. フォーク元 `satory074/todayai` をベースにした

**決定**: ゼロから作らず、AI 情報集約サイト `satory074/todayai` をベースに、セキュリティ情報向けへ
改造する形で構築する。**作者の許諾は取得済み。**

**理由**:

- 運用者は開発未経験。「RSS を集めて時系列で並べる静的サイト」に必要な部品
  （集約パイプライン・OGP 補完・保持ポリシー・CI・Pages デプロイ）が既に動く状態で揃っており、
  **学習の出発点として実物が動いていることの価値が大きい**。
- ソースの差し替えが設計上想定されている（`feeds.config.ts` ＋ `SOURCES` 配列の中心レジストリ）ため、
  「AI → セキュリティ」の付け替えが構造変更なしで済む見込みだった。実際そのとおりだった。
- 費用 0 円という制約を最初から満たしていた（公開 RSS ＋ GitHub Pages）。

**却下した案**:

- **ゼロから自作** — 学習効果は高いが、動くまでの距離が遠い。CI・デプロイ・OGP 解決のような
  「本題ではないが必須」の部分で止まるリスクが高いと判断した。
- **GitHub の fork 機能を使う** — 採用せず、コードをベースにした独立リポジトリにした。
  fork のままだと本家への PR が既定動作になり、無関係な改造履歴を持つリポジトリとして扱いにくい。

**再検討すべき条件**:

- 本家の設計（集約→マージ→トリム→補完の2フェーズ構成）が、セキュリティ用途の要求と
  合わなくなったとき。現状は合っている。
- **フォーク元由来の残骸が見つかったとき**は再検討ではなく単純に修正する。URL・アカウント名の
  ハードコードが複数あった（CLAUDE.md「フォーク元からの変更点」表）。同種のものは同じ方針で直す。
- ⚠️ `docs/gcs-storage-setup.md` には**フォーク元の GCP プロジェクト名・バケット名が残っている**。
  これは「使っていない手順書」として意図的に残しているもので、流用するなら自分の環境で作り直す。

## 2. 4ソースを削除し、X だけ温存した

**決定**: `hatena`（はてなブックマーク）/ `layerx` / `workspace`（Google Workspace Updates）/
`gcloud`（Google Cloud リリースノート）を**コードごと削除**。`x` は削除せず
**`disabled: true` で温存**する。

> ⚠️ **依頼時の記憶と実際の履歴に食い違いがあったので、履歴側に合わせて書いている。**
> 「X / LayerX / GCP / Workspace を削除」ではなく、**削除された4つ目は `hatena`（はてなブックマーク）**
> で、**X は削除していない**（`0e43fa2 refactor: 使わない4ソース（hatena/layerx/workspace/gcloud）を削除`、
> および `1d23902 chore: X / LayerX / translate を無効化`）。X は最初に無効化され、その後の
> 削除対象からは外れた、という順序。

**理由**:

- 削除した4つは**セキュリティ用途に内容が合わない**（Workspace/gcloud はクラウド製品の更新情報、
  layerx は AI ニュースレター、hatena はテック全般の人気エントリー）。
  無効化して残すと、`feeds.config.ts` と `SOURCES` の対応を読むたびに「これは何だったか」を
  考えるコストが毎回かかる。
- **layerx / workspace / gcloud は運用コストも高かった**（Gmail OAuth のリフレッシュトークン失効、
  FeedBurner への 302、1エントリ＝1日の専用パーサ）。セキュリティ用途で使わないものに
  この保守を抱える理由がない。
- **X だけ温存したのは、無効化の理由が「内容が合わない」ではないから。** X の停止理由は
  ①既定の取得先がフォーク元作者の公開ブックマーク JSON で、自分のデータではない
  ②外部アカウント取得は X API 有料 — の2点であり、**セキュリティ情報の収集手段としては今も有効**。
  取得先さえ差し替えれば使える状態を残しておく価値がある。
- 削除したものも**要点だけは CLAUDE.md に残し、削除コミット `0e43fa2`（その直前が `c5c9547`＝
  削除前の実装が読める状態）を添えた**。
  「はてブ人気エントリーは今人気の約30件しか返さない → 前回分を土台に蓄積する設計が必須」という
  知見は、**今も全ソース共通の仕組みとして生きている**（この設計の由来が分からなくなるのを防ぐ）。

**却下した案**:

- **4ソースも `disabled: true` で温存** — 温存はタダではない。型・設定・専用スクリプト・
  `.env.example`・CI の env が残り続け、読む人が「有効か無効か」を毎回判定することになる。
  復活可能性が実質ゼロのものは消したほうが読める。
- **X も削除** — 上記のとおり停止理由が違うので却下。
- **X の取得先を自分のアカウントに差し替えて有効化** — X API が有料のため費用 0 円の方針に反する。
  無効のまま温存が現実的。

**再検討すべき条件**:

- **X**: 無料または十分安価にセキュリティ関連アカウントのポストを取れる経路ができたとき。
  復活させるときは `disabled: false` だけでは画面に出ない（CLAUDE.md「無効化したソースを
  復活させるとき」の4手順が必要）。
- **削除した4つ**: 復活はまず無い。仮に必要になっても `git show 0e43fa2^:scripts/sources/<name>.ts`
  （`0e43fa2^` = `c5c9547`）で実装を読み直せる。
- **温存している `x` のコードが改修の足かせになったとき**（型やパイプラインの変更のたびに
  無効なコードの面倒を見る負担が無視できなくなったら）、温存をやめて削除に倒す。

## 3. はてなブログはタグ横断をあきらめ、個別ブログを列挙する

**決定**: 「セキュリティタグの新着を全ブログ横断で取る」フィードの利用を断念し、
**セキュリティ専門の個別ブログ3本の Atom を列挙**する（`feeds.config.ts` の `hatenablog.rssUrls`）。

**理由**:

- **横断フィードが存在しないことを実アクセスで確認した。** `hatenablog.com/tag/<tag>` は
  `hatena.blog/tag/<tag>` へ 301 したうえで **404**。`/feed`・`?mode=rss`・`.rss`・`/tags/`・
  `/topic/`・`/g/`・`blog.hatena.ne.jp/-/search` もすべて 404（詳細は CLAUDE.md「ソース別の要点」）。
  **推測ではなく実測の結果として無い**。
- 個別列挙は**質が担保できる**という副次的な利点がある。piyolog / Fox on Security /
  GMO Flatt Security はいずれもセキュリティ専門で、横断タグより S/N が高い。
- 増やすのが簡単（`rssUrls` 配列に足すだけ。`limit` は 1 URL あたりなので既存分が痩せない）。

**却下した案**:

- **はてなブックマークの検索 RSS（`b.hatena.ne.jp/q/<word>?mode=rss`）で代替** — 唯一横断で取れる
  経路だが、これは**ブログ記事ではなくブックマーク**＝削除した `hatena` 枠と同じもの。
  「はてなブログ」ソースの中身がブックマークになるのは筋が悪い。
  ただし**ブログ候補を探す用途には有効**（セキュリティ関連語で引いてはてなブログ系ホストを集計する）。
- **網羅性を優先して一般的なはてなブログを広く入れる** — ノイズが増える。当時は
  「件数を増やすより探すコストを上げない」を優先していた（この優先順位は後に項目11で見直している）。

**再検討すべき条件**:

- **はてな側が横断タグフィードを提供したとき。** ⚠️ そのときは
  **CLAUDE.md に記録した「404 だった」という事実から確認し直すこと**（過去の調査結果を
  そのまま信じない）。
- 個別ブログが更新停止・移転したとき。列挙方式は**ブログが死んでも気づけない**のが弱点で、
  ソース別件数が 0 のまま続いていないかを時々見る必要がある。
- 列挙するブログが増えすぎて管理しきれなくなったとき（10本を超えるなら方式を考え直す）。

## 4. Astro 5 → 7 のアップグレードを後回しにする

**決定**: `astro ^5.1.0` のまま据え置く。報告されている脆弱性8件を個別に評価し、
**このサイトには該当しない**と判断した。

**理由**:

- **8件のうち7件は、使っていない機能の脆弱性**だった: `define:vars` / spread props /
  View Transition / Server island / SSR エラーページ。
  **`src/` を実際に検索して不使用を確認済み**（`define:vars`・`{...spread}`・
  `ViewTransitions`/`ClientRouter`/`transition:`・`server:defer` いずれも 0 件。
  `astro.config.mjs` に adapter が無く `output` 指定も無い＝純粋な SSG で SSR エラーページも存在しない）。
- **残る1件（esbuild の開発サーバー）だけが該当**。ただし影響するのは
  **`npm run dev` を実行している間だけ**で、ビルド成果物にも公開サイトにも影響しない。
  **静的サイトなので露出面が構造的に小さい**（実行時にサーバーが存在しない）。
- 対して**メジャーバージョン2つ分の移行はコストとリスクが大きい**。運用者は開発未経験で、
  ビルドが壊れたときの復旧が難しい。**利得（該当しない脆弱性の解消）に見合わない**。
- 代わりに**運用でリスクを潰した**: 「dev サーバーを確認後に必ず停止する」を
  CLAUDE.md の標準ルールに明記（過去に複数ポートに溜まる問題が実際に起きたため）。

**却下した案**:

- **すぐ astro 7 へ上げる** — 上記のとおりコスト過大。
- **`npm audit fix --force` で強制解決** — メジャー更新が無警告で入り、壊れ方が読めない。
  なお通常の `npm audit fix` は実施済み（`98ad263`、12件→3件）。
- **dev サーバーを使わない運用にする** — 表示確認ができなくなり、実害のほうが大きい。

**再検討すべき条件**（⚠️ **この項目は前提が最も崩れやすい**）:

- **使っていないとされた機能を使い始めたとき。** 具体的には:
  - `set:html` を使うコンポーネントを追加したとき（**現在 0 件**。RSS 本文の HTML をそのまま
    描画したくなった場面で踏みやすい）
  - **spread props（`{...props}`）を使うコンポーネントを追加したとき**（現在 0 件。
    共通コンポーネントを抽象化すると自然に出てくる書き方）
  - View Transition（`ClientRouter`）を入れたくなったとき
  - `define:vars` でサーバー側の値をインラインスクリプトへ渡したくなったとき
- **SSR / Server island を有効化したとき**（adapter を入れて `output` を変えたとき）。
  静的サイトという前提が崩れるので、**この項目の判断は丸ごと無効になる**。
- 新たに報告された脆弱性が**ビルド時または成果物に影響するもの**だったとき。
  「dev サーバーのみ」でなくなった時点で評価をやり直す。
- astro 5 のセキュリティサポートが終了したとき。

## 5. Gemini は3行要約に使わず、翻訳だけに使う

**決定**: `translate` は有効（`disabled: false`）だが、**`summarizeSources` は空**のままにする。
＝**非日本語の記事だけ翻訳し、要約はしない。**

**理由**:

- **トークン消費が約16倍違う。** 要約は**記事本文 7,000〜10,000 字**が入力になるのに対し、
  翻訳は**タイトル＋抜粋の約 500 字**。無料枠で回すという前提では差が大きすぎる。
- **日本語ソースは `isJapanese()` でスキップされ、そもそも API を呼ばない。**
  一方 `summarizeSources` に入れると**原文の言語を問わず要約対象**になる＝
  **日本語記事にまで API を使うことになる**（Zenn/Qiita/はてなブログが全部対象になる）。
  「英語ソースだけ 1日4〜6リクエスト」という費用感が崩れる。
- 解きたかった問題は「**英語の見出しが読めない**」であって「日本語記事が長い」ではない。
  翻訳だけで問題は解ける。

**却下した案**:

- **記事系ソースを `summarizeSources` に入れて3行要約する** — 上記のトークン量に加え、
  **要約は誤りが混入したときに気づきにくい**（翻訳は原文と1対1で照合できるが、
  要約は「書いていないこと」が混ざっても検出しにくい）。個人の学習目的のサイトで
  AI 生成の要約を一次情報のように見せるのは避けたい。
- **翻訳ごと無効にする（原文のまま並べる）** — 英語ソースが増えて英語の見出しが並び、
  見出しだけで取捨選択できない状態になったため却下。
  ⚠️ **当時「新着の約8割が英語」と書いていたが、これは実測されていない数字だった。
  実測は 51%（Qiita の API 化後は約44%＝日本語が過半数）**。翻訳を有効にした判断自体は
  変わらない（英語が半分あれば見出しが読めない問題は起きる）が、**根拠の数字は誤りだった**
  ＝この種の「体感で書いた比率」は疑うこと（項目9・項目19 も同じ罠を踏んでいる）。

**再検討すべき条件**:

- **無料枠の条件が変わったとき**（拡大すれば要約を試す余地が出る。縮小すれば翻訳自体を見直す）。
- **抜粋が短すぎるソースが主力になったとき。** Dark Reading の抜粋は 69〜219 字（中央 148 字）＝
  ほぼ1文しかなく、翻訳しても内容が分からない。こういうソースが増えるなら、
  **`enrichArticles` が取る記事本文を使った要約**に価値が出る。
- ⚠️ **`summarizeSources` を変えるときは `aggregate.ts` の `ENRICH_VERSION` を必ず上げる**
  （上げないと翻訳済みキャッシュが再生成されず、変更が反映されない）。
- 翻訳が出なくなったときは方針の問題ではなく **Gemini の HTTP 4xx を疑う**
  （モデル提供終了で 429 になった前例あり。CI は緑のまま静かに壊れる。CLAUDE.md 参照）。

## 6. API キーはローカル `.env` に置かず、GitHub Secrets のみに置く

**決定**: `GEMINI_API_KEY` は GitHub Secrets にのみ設定する。**ローカルの `.env` には置かない。**

**理由**:

- **このリポジトリは Public。** 誤コミットが即座に公開される。
- **「置かなければ漏れない」という構造的な排除**を選んだ。`.gitignore` や
  コミット前チェックは**運用者の注意力に依存する**が、そもそもローカルに秘密が存在しなければ
  誤コミットは原理的に起こらない。運用者は開発未経験で、注意力に頼る対策は破綻しやすい。
- **実害がない。** ローカルで必要なのは表示確認（`npm run dev`）であり、これは
  コミット済みの `src/data/feed.json` があれば動く。**翻訳は CI で走れば十分**。
- ローカルで翻訳が走らない＝`titleJa` が付かないだけで、`state.translations` から
  再適用されるので**データが壊れることもない**（graceful degradation）。

**却下した案**:

- **`.env` に置いて `.gitignore` で守る** — 一般的なやり方だが、上記のとおり注意力依存。
  Public リポジトリでの事故のコスト（キーの失効・再発行）に見合わない。
- **キーを環境変数として都度エクスポートする** — 漏洩リスクは下がるが手順が煩雑で、
  そこまでしてローカルで翻訳を走らせる必要がない。

**再検討すべき条件**:

- **リポジトリを Private にしたとき**（前提そのものが変わる）。
- **ローカルで翻訳の挙動を検証する必要が出たとき**（プロンプトの調整など）。
  そのときも「常設せず、検証中だけ環境変数で渡し、終わったら消す」を優先する。
- ⚠️ **`.env` / `.env.example` は書き込みできない。**
  変更が必要なら手作業で対応する（CLAUDE.md の標準ルール「触ってはいけないもの」）。

## 7. 説明文・フィルタ・about を `SOURCES` から自動生成する

**決定**: ソース一覧を表示するすべての箇所（トップの説明文・フッター・`<meta description>`・
フィルタチップ・about ページ・RSS の description）を、`src/lib/feed.ts` の `SOURCES` 配列から
生成する（`661d10d refactor: ソース一覧の表記を SOURCES から自動生成する`）。

**理由**:

- **手動更新の漏れが実際に発生した。** はてなブログを追加したとき、コードは全部直したのに
  **README と説明文が「Zenn と Qiita から集約」のまま残った**。
  同じ情報が複数箇所に散っていると、ソースを足すたびに全部を思い出す必要がある。
- ⚠️ **同じ漏れがその後も起きた。** 翻訳を有効化したとき（`e29e520`）、**README が
  「トークン・API キーは不要です」「Secrets の設定は不要です」「Gemini API は無効化」のまま
  残り、同じ README 内の「Gemini による翻訳が有効」という記述と矛盾した**。
  ＝**自動生成の対象は「ソース一覧の表記」だけで、「機能の有効・無効」は自動追従しない**。
  こちらはチェックリスト側で受ける（CLAUDE.md「機能を有効化・無効化するときのチェックリスト」）。
- ソースの追加は**このサイトで最も頻度の高い作業**。1回の追加で直す箇所が多いほど漏れる。
- `SOURCES` は既に「今どのソースを集めているか」の中心レジストリになっていた＝
  **新しい仕組みを作るのではなく、既にある単一の真実を参照させるだけ**で済んだ。

**却下した案**:

- **手動のまま、チェックリストで漏れを防ぐ** — チェックリストは作ったが、それだけでは不足。
  **自動化できるものは自動化し、チェックリストは自動化できないものに集中させる**ほうが機能する
  （現に CLAUDE.md のチェックリストは「自動で追従するもの」と
  「手で更新が必要なもの ★ここが漏れやすい」を明確に分けている）。

**再検討すべき条件**:

- ソースごとに**説明文を個別に出し分けたくなったとき**（自動生成は一律の書式になる）。
  そのときも `SOURCES` にフィールドを足す方向で解決し、表示側にベタ書きしない。
- ⚠️ **README.md / CLAUDE.md / OGP 画像は自動追従しない。** ここは今も手作業で、
  実際に漏れる場所。CLAUDE.md のチェックリスト「3. 手で更新が必要なもの」を必ず通す。
  **機能のフラグを動かしたときは別のチェックリスト**（CLAUDE.md「機能を有効化・無効化するときの
  チェックリスト」）を通す。
- ⚠️ **数字や個別列挙を書かない方針にした。** 「N ソース」「A / B / C の3つ」という書き方が
  4回取り残されたため、README / CLAUDE.md から件数とサイト名の列挙を削り、
  表・`SOURCES`・`feeds.config.ts` を参照する形に変えた。**新しく書き足さないこと。**

## 8. 言語トグルは削除せず、条件付き表示にする

**決定**: 「日本語 / 原文」トグルを、翻訳データが1件も無いときは描画しない
（`hasAnyTranslation(items)` が true のときだけ出す。`c43c3b0`）。

**理由**:

- 翻訳を無効にしていた時期、トグルは**押しても何も起きない飾り**になっていた。
  機能しない UI は「壊れている」という印象を与える。
- **削除すると、翻訳を有効化したときに作り直しになる。** 翻訳は温存する方針だったので、
  復活が前提だった。
- 条件付き表示なら**翻訳を有効化した瞬間に自動で復活する**＝
  「有効化したのにトグルが出ない」という第二の事故が起きない。
  実際、翻訳を有効化したとき（`e29e520`）にトグル側の作業は不要だった。

**却下した案**:

- **トグルを削除する** — 上記のとおり作り直しになる。
- **無効状態でも常に表示する** — 押しても何も起きない UI が残る。
- **フラグで手動制御する** — 項目9と違い、ここは**データを見れば自動判定できる**
  （翻訳が存在するかどうか）。判定できるものを人間の設定に落とすと、
  設定と実態がズレる余地を作ることになる。

**再検討すべき条件**:

- 翻訳を**恒久的にやめると決めたとき**（そのときは実装ごと削除してよい）。
- ⚠️ **`isTranslated` / `hasAnyTranslation` はこのトグル専用ではない。**
  `BilingualText` の表示判定にも使われているので、消すときは巻き込みを確認する。

## 9. 「日本語」フィルタは、追加したあと使ってみて非表示にした

**決定**: 「日本語」フィルタチップを追加した（`06ad4d1`）が、実際に使ってみて不要と判断し、
**削除ではなく `SHOW_LANG_FILTER_CHIP = false` で表示だけ止めた**（`d719f29`）。

**理由**:

- 追加した動機は「英語ソースが増えて日本語記事が埋没する」だった。
  しかし**使ってみると、実際にはそのフィルタを押さなかった**。翻訳が有効で日本語の見出しが
  付いているため、埋没の体感がそれほど無かった。
- ⚠️ **前提として書いていた「新着の約8割が英語」は誤りだった。実測 51%**（取り込み件数ベース）。
  **さらに Qiita の API 化（項目19）で日本語の取り込みが増え、約44% になる＝日本語が過半数。**
  ＝ **埋没対策としての必要性は当初の想定より低い**。
  **非表示のままでよい**という結論は変わらない（むしろ補強された）が、
  **復活を検討するときは体感ではなく実測から始めること**。
- **「作ってから使ってみないと分からない判断だった」ことを記録しておきたい。**
  机上では必要に見えたが、実運用では不要だった。
- **削除せずフラグにしたのは、前提が季節変動するから。** 蓄積が進んで英語記事の比率が
  さらに上がれば、また必要になりうる。**作り直しを避けたい。**
- **フラグで止めても副作用がない**ことを確認済み: フィルタ JS はチップの `data-filter-kind` を
  見るだけで「日本語」チップの存在を前提にしていない。またフィルタの選択状態は
  `localStorage` に保存していない＝**「日本語」を選んだ状態で再訪して壊れる経路が存在しない**。

**却下した案**:

- **削除する** — 上記のとおり復活の可能性があり、判定ロジック（`isTranslated`）と
  記事側の目印（`data-orig-lang`）も含めて消すと復元コストが高い。
- **そのまま表示し続ける** — 押さないチップがフィルタ列を占有する。フィルタは
  `flex-wrap` で行数が変わるため、不要なチップは**レイアウトにも影響する**。
- **項目8と同じく自動判定にする** — できない。「翻訳データがあるか」は判定できるが
  「このフィルタが有用か」は判定できない。**人間の判断が必要なのでフラグが妥当**。

**再検討すべき条件**:

- **日本語記事の埋没が体感できるようになったとき**（英語ソースをさらに増やしたとき、
  日本語ソースの更新が止まったとき）。`true` に戻すだけで復活する。
  ⚠️ **そのときは「英語の比率」を実測してから判断する**（上記のとおり体感の数字が2倍ずれていた）。
- 翻訳を無効化したとき（英語のまま並ぶので埋没が一気に顕在化する）。

## 10. バッジ色はグループ配色にせず、個別色を続ける

**決定**: ソースが増えて色差の基準を満たせなくなったが、**グループ配色（国内/海外で色を共有）へは
移行せず、ソースごとに個別色を割り当て続ける**。

**理由**:

- かつての合格基準は「**既存どうしの最小色差 ΔE 58.3（Qiita↔ロゴ）を上回る**」で、
  7色目までは満たせた。しかし **8色目 The Register で ΔE 48.3、9色目 HackRead で 47.4** と
  **2回連続で基準未達**。
- **これは努力で解決できない。** 色相環は 360° しかなく、白背景で AA 4.5:1 を満たす明度帯も限られる。
  明度・彩度を動かして全色相を総当たりしても**上限は 48 前後**だった。
  ＝**基準のほうが維持不能**であり、基準を守るために設計を変えるのは本末転倒。
- **バッジには常に「ソース名の文字」が入る。** 色は判別の**主役ではなく補助的な手がかり**だと
  割り切れば、ΔE が下がっても実用上の問題は小さい。
- 個別色をやめると**「どのソースか」を色で大まかに掴む手がかりが完全に失われる**
  （グループ配色では The Hacker News と Dark Reading が同色になる）。得るものより失うものが大きい。

**却下した案**:

- **グループ配色（国内/海外メディアで数色を共有）** — 基準は満たせるが上記のとおり情報量が落ちる。
  ⚠️ ただし**移行方法は分かっている**: `SourceMeta` に `group` を足して `badgeClass` を
  グループ由来にするだけ（`SOURCES` 駆動の自動追従はそのまま使える）。方針を変えるときのために記録。
- **基準を満たすまで色を探し続ける** — 総当たりで不可能と確認済み。
- **基準を下げて「達成」したことにする** — 数字を都合よく動かすと基準が意味を失う。
  **未達は未達として記録し、そのうえで続ける**と決めた（各色のコメントに
  「何色目で・どの色と・どれだけ近いか」を残している）。

**再検討すべき条件**:

- **ソースがさらに増えて、色が実用上まったく区別できなくなったとき。**
  目安として ΔE が 40 を切るあたり、または**運用者自身が色で見分けられないと感じたとき**。
  そのときはグループ配色へ移行する（上記の移行方法）。
- **バッジからソース名の文字を消す変更をしたとき** — この判断の前提（文字があるから色は補助）が
  崩れる。**そのときは色が唯一の手がかりになるので、この決定は無効**。
- ダークテーマを追加したとき（白背景前提のコントラスト計算をやり直す必要がある）。

## 11. HackRead は一度見送ったあと、ノイズを承知で採用した

**決定**: 調査時に一度**見送った** HackRead を、方針を変えて**採用**した。
**除外の仕組みは意図的に作っていない。**

**理由**:

- **一度見送った理由**: ノイズが多い。取得10件のうち**セキュリティ報道は4件程度**で、
  残りは「Top 10 Companies to Hire Power BI Developers in 2026」のような
  **セキュリティ無関係の SEO 記事**と、`dc:creator` が `CyberNewswire` の**プレスリリース転載**。
  当時は「件数を増やす」より「探すコストを上げない」を優先していた。
- **採用に転じた理由**: **除外が本当に必要か、どの条件が適切かは、机上では決められない**と考え直した。
  1週間ほど運用して実態を見てから判断するほうが確実。**ノイズを含んだまま入れて様子を見る。**
- **除外を先に作らなかったのは、作ると判断材料が消えるから。** 除外条件を入れた状態で運用すると
  「除外しなければどうだったか」が分からなくなる。**まず観測し、それから決める。**
- 項目3で採った「件数より S/N」という優先順位を、ここでは**意図的に逆にしている**。
  この不一致は認識したうえでの選択（HackRead は速報性があり、S/N の低さと引き換えに得るものがある）。

**却下した案**:

- **見送ったまま採用しない** — 判断材料が得られない。
- **除外条件を実装してから採用する** — 上記のとおり観測を潰す。加えて
  「ソースごとの除外条件」の仕組みを `rss.ts` に持たせる必要があり、**別作業**の規模になる。

**再検討すべき条件**（⚠️ **これは「いつか」ではなく「近いうちに必ず」再検討する項目**）:

- **1週間ほど運用したら、実態を見て除外の要否を判断する。** これが採用の前提条件。
  **判断せずに放置すると、「ノイズを承知で採用した」が「ノイズに慣れた」に変わる。**
- 除外すると決めたときの実装候補は2つ:
  1. `dc:creator` が `CyberNewswire` のものを除外（PR記事はこれでほぼ落ちる）
  2. `categories` による除外（フィードが categories を持つので技術的に可能）
- ✅ **「別作業」としていた「ソースごとの絞り込み条件」の仕組みは、項目24（CloudNative）で
  実装済み**（`rss.ts` の `RssItemFilter` ＋ `matchesFilter`、`feeds.config.ts` の `filter`）。
  ＝ **HackRead の除外は実装可能になった。ただし実装はしていない**（除外するか自体が未決のため）。
  - 現状あるのは**含める条件（`includeCategories`）だけ。** HackRead に必要な
    「`dc:creator` が `CyberNewswire` を除外」は**除外側**なので、
    `RssItemFilter` に `excludeAuthors` を足し、`matchesFilter` に数行加え、
    さらに `RssItem` に `creator`（rss-parser の `dc:creator`）を取り込む必要がある。
  - ⚠️ **仕組みができたことは「除外すべき」という判断ではない。** 上の
    「1週間ほど運用して実態を見てから判断する」が先。
  - ⚠️ **項目24 の使い分けを必ず読むこと**＝ HackRead のノイズは「**質が低い**」タイプで、
    CloudNative で絞った「**話題が違う**」タイプとは別問題。混同すると
    「ノイズが多いから絞る」という誤った理由付けになる。
- ノイズ比率が悪化したとき、または**除外の仕組みを作るコストが見合わないと判断したとき**は
  ソースごと外す選択肢もある。
- ⚠️ フィードは10件しか返さず、実測 5.6件/日 なので**約1.8日分**しか遡れない＝
  **CI が2日止まると取りこぼす。全ソースで最も余裕が薄い**
  （BleepingComputer 約2.4日分がその次。一覧は CLAUDE.md の「フィードから何日分遡れるか」）。
- ⚠️ **「ノイズがあるソースを入れる／入れない」と「質が低い記事を除外する」は別問題。**
  ここで許容したのは**セキュリティと無関係な記事**（SEO 記事・PR 転載）が混ざることであって、
  「セキュリティの話だが初心者向け」を落とす話ではない。**この使い分けは項目19 に書いてある**
  （Qiita で入門記事を除外しなかった判断）。混同すると対象内の記事まで削ることになる。

## 12. The Register はセキュリティセクション限定フィードを使う

**決定**: 全体フィードではなく **`/security/headlines.atom`（セクション限定）** を使う。
かつ設定ファイルには**リダイレクト前の「人が読める URL」を書く**。

**理由**:

- The Register は**総合 IT メディア**で、クラウド・ハードウェア・企業ニュース・宇宙開発まで扱う。
  全体フィード（`/headlines.atom`）ではセキュリティ以外が大量に混ざる＝
  **このサイトの目的（セキュリティ情報）に合わない**。
- セクション限定フィードは**実測 50 件すべてがセキュリティ関連**だった（タイトル全件を目視確認）。
- **人が読める URL を書くのは、転送先が壊れやすいから。** 実際には
  `api.theregister.com/api/v1/article?...&query=tag:security` へリダイレクトするが、
  この URL は `site_id=2` / `remapper=rss` といった**内部パラメータを含む**。
  サイト側の都合で変わったときに、内部 URL を直書きしていると原因が分かりにくい。
- ⚠️ **The Hacker News とは逆の判断をしている。** あちらは最終 URL（FeedBurner）を直接書いた。
  **転送先が安定した公開エンドポイントかどうかで使い分けている**（FeedBurner は公開サービス、
  The Register の api.theregister.com は内部 API）。この使い分けは意識的なもの。

**却下した案**:

- **全体フィードを使って件数を稼ぐ** — 目的に合わない記事が主になる。
  項目11（HackRead）でノイズを許容したのとは事情が違い、こちらは**セクション限定という
  正しい解が存在する**（ノイズを避ける手段があるのに使わない理由がない）。
- **最終 URL（`api.theregister.com/...`）を直接書く** — リダイレクトを1回減らせるが、
  内部パラメータへの依存が増える。

**再検討すべき条件**:

- **セクションフィードの内容が変質したとき**（セキュリティ以外が混ざり始めたら、
  全件目視の再確認をやり直す）。
- **`/security/headlines.atom` が 404 になったとき。** ⚠️ 他の形
  （`/security/feed/`・`/security/rss`・`/security/atom.xml`・`/security/index.atom`）は
  **すべて 404 と確認済み**なので、そこを試し直すのは無駄。同内容を返すのは
  `/security/headlines.rss` のみ。
- リダイレクト先が変わって取得が不安定になったとき（そのときは最終 URL 直書きを再評価する）。

## 13. `feed.json` は git 保管のままにし、GCS モードへ移行しない

**決定**: `feed.json` を `src/data/feed.json` として git にコミットする運用を続ける。
**GCS 保管モードは実装が存在するが有効化しない**（リポジトリ変数 `GCS_BUCKET` 未設定）。

**理由**:

- **費用 0 円という方針が最優先。** GCS は料金が発生しうる。
- git 保管なら**履歴がそのまま追える**し、壊れたときに `git show` で過去の状態を取り出せる。
  開発未経験の運用者にとって、**確認手段が git だけで完結する**のは大きい。
- 手順書（`docs/gcs-storage-setup.md`）は**フォーク元の GCP 設定のまま**で、
  そのままでは動かない＝移行には実質的な作り直しが必要。

**却下した案**:

- **GCS へ移行する** — 6時間ごとのコミットループが消える（履歴が feed の更新で埋まらない）
  という明確な利点があるが、費用とセットアップコストが方針に合わない。

**再検討すべき条件**:

- **リポジトリサイズが実用上の問題になったとき**（`feed.json` は蓄積し続ける設計で、
  6時間ごとに全文がコミットされる＝履歴が単調に増える）。
- コミット履歴が `chore: update feed` で埋まって**人間の変更が追えなくなったとき**。
- ⚠️ 移行するなら手順書の GCP プロジェクト名・バケット名を**自分の環境で作り直す**こと。

## 14. 年齢による削除をやめ、ソース別の件数上限にした

**決定**: 「N 日より古いものを消す」（旧 `maxAgeDays`）を**廃止**し、
**ソースごとの件数上限 `retentionMax`** を唯一の上限にする。

**理由**:

- **ソース別の枠にしないと、物量の多いソースが他を押し出す。** 全体で一律の上限だと、
  1日10件の The Hacker News が、週数件のはてなブログを押し流してしまう。
- 年齢での削除は**「古いが価値のある記事」を機械的に捨てる**。セキュリティ情報は
  数ヶ月前のインシデント記事にも参照価値がある。
- 全ソースが「前回分を土台に蓄積する」設計になっているため、
  **取得窓が狭い RSS でも過去分が失われない**という利点を、年齢削除が打ち消していた。

**却下した案**:

- **全体で一律の件数上限** — 上記のとおりソース間で不公平になる。
- **上限なし（無限に蓄積）** — `feed.json` が肥大しビルド時間と git 履歴に響く。

**再検討すべき条件**:

- `feed.json` のサイズがビルド時間や表示速度に影響し始めたとき。
- **ソースごとの投稿頻度が大きく変わったとき**（`retentionMax` は頻度から逆算した値。
  既定 1000 は約10件/日なら3ヶ月分という見積もり）。
  ⚠️ **Qiita は API 化（項目19）で取り込みが 4件/run → 実質全件（14〜23件/日）になった**＝
  `retentionMax: 1000` は**約3ヶ月分ではなく約50日分**。他ソースより先に上限に当たるので、
  アーカイブを長く持ちたいならここを上げる。

## 15. ロゴの色だけ専用変数に分離した

**決定**: ロゴをエメラルドグリーン `#0f9b6c` に変更する際、
**サイト全体のアクセント色（コバルト `#2f5fff`）は変えず**、`--color-logo` 系の専用変数を新設した。

**理由**:

- `--color-accent` は**フィルタチップ・言語トグル・カード hover が共有している**。
  ロゴを変えるつもりで触ると**サイト全体が巻き込まれる**。
- 「ロゴだけ変えたい」という意図を**変数の構造として表現しておく**ことで、
  次に触る人（＝将来の自分）が事故らない。

**却下した案**:

- **`--color-accent` を直接変更する** — サイト全体が緑になる。意図と違う。
- **ロゴにハードコードで色を書く** — 変数管理から外れ、変更箇所が追えなくなる。

**再検討すべき条件**:

- **サイト全体の配色を刷新すると決めたとき**（そのときは分離の意味が薄れる）。
- ⚠️ Tailwind v4 は**実際に使われている `@theme` 変数しか CSS に出力しない**ので、
  `--color-logo-bright` / `-deep` は定義済みでもビルド後の CSS には現れない。**不具合ではない。**

## 16. アクセス解析は Cloudflare Web Analytics を使う

**決定**: Cloudflare Web Analytics（Cookie 不要）を使い、**トークン未設定でも動く**形にする。

**理由**:

- **Cookie を使わない**＝同意バナーが要らない。個人の学習目的のサイトに同意管理を持ち込みたくない。
- **トークンは公開値**（ページソースに出る）なので Secret ではなく**リポジトリ変数**で扱える
  （`PUBLIC_` 接頭辞は Astro/Vite のクライアント露出に必須）。項目6の「秘密を増やさない」方針と整合する。
- **未設定ならタグを出力しないだけ**でビルドは壊れない（graceful）。
  設定しないまま運用を始められる。

**却下した案**:

- **Google Analytics** — Cookie と同意対応が必要。個人サイトには重い。
- **解析を入れない** — 「誰も見ていないのか、見られているのか」が分からないと改善の判断ができない。

**再検討すべき条件**:

- Cloudflare Web Analytics が有料化または終了したとき。
- ページ単位より**詳細な分析が必要になったとき**（現状は必要ない）。

## 17. テストフレームワークを導入しない

**決定**: テストフレームワークを入れない。検証は `npm run typecheck` / `npm run build` と
`npm run aggregate` の実行ログ（ソース別件数）で行う。

**理由**:

- **このサイトのロジックの大半は「外部フィードを取ってきて並べる」**で、
  壊れるとしたら**外部の都合**（フィードの形式変更・404・レート制限）。
  これはユニットテストでは検出できず、**実際に取得してログを見る**しかない。
- **型検査が実質的なテストとして機能している**（`tsconfig` の `include: ["**/*"]` により
  `scripts/` も `astro check` で検査される）。
- 運用者は開発未経験。**テストの保守自体が学習コストになり、本題から逸れる**。

**却下した案**:

- **Vitest 等を入れて主要関数をテストする** — `truncateSafe` や `isJapanese` のような
  純粋関数にはテストが書けるが、**壊れて困っているのはそこではない**。
- **E2E テスト** — 静的サイトで JS も最小限。費用対効果が低い。

**再検討すべき条件**:

- **純粋なロジックが増えたとき**（除外条件の実装＝項目11 は、まさにテストが有効な種類のコード。
  「この記事は除外されるか」は入出力が明確でテストしやすい）。
- **同じ不具合を繰り返すようになったとき**（回帰テストが必要というサイン）。
- ⚠️ **`npm run build` は Astro が import するファイルしか型検査しない。**
  `scripts/` を変更したら**必ず `npm run typecheck` を通す**（現状これが唯一の検査手段）。

## 18. OGP 画像は手で作らず、コードから生成する

**決定**: `public/og-default.png` を `scripts/generateOgImage.ts`（SVG 組み立て → sharp で PNG 化）で
生成する。**手で画像を差し替えない。**

## 19. Qiita だけ公開 RSS をやめ、Qiita API v2 を主経路にする

**決定**: Qiita のタグ別新着を**公開 RSS ではなく Qiita API v2（認証不要）で取得する**。
RSS は**削除せずフォールバックとして残す**（429/403・障害時に自動で切り替わる）。
**cron は6時間のまま据え置く。**

**理由**:

- **RSS では記事の 47% を失っていた**（実測: 5.8日で132件中62件）。原因は
  **Qiita のタグフィードが4件しか返さないこと**。タグを問わず固定で、`?page` / `?per_page` は
  無視される（security / 認証 / python / aws / javascript すべて4件・実アクセスで確認）。
  ＝ **`limit: 20` は Qiita に対して一度も効いたことがなかった。**
- **Security タグは 14〜23件/日 投稿されるので、4件の窓は中央値 3.3 時間**しかない。
  cron は6時間ごと（実測 5.4〜7.1時間間隔）なので**毎 run 溢れていた**。
  feed.json のコミット履歴でも**毎 run きっちり +4件**で、20件取り込めた run は1つもなかった。
- **「運で消えている」状態は容認できない。** 47% を失うこと自体より、**質と無関係に半分が
  ランダムに落ちること**が問題だった（質でフィルタしているのではない）。
- API は**1リクエストで最大100件**返るので、窓を「時間」から「日」の単位にできる。
  **副産物として、後からタグを追加された過去記事も拾える**（API の一覧は created_at の
  厳密降順ではない。実測で最新300件中5件）＝ created_at 順の RSS では構造的に不可能だった。
- **費用 0 円のままで、秘密も増えない**（認証不要）。項目6の「秘密を増やさない」方針と整合する。

**却下した案**:

- **cron を短くする（6時間 → 2〜3時間）** — ⚠️ **単独では解決しない。** 実測で、4件の窓を
  超過する区間は **cron 3時間で46%・2時間で31%・1時間でも17%** 残る。ゼロにするには
  10〜15分間隔が必要で、GitHub の scheduled run は混雑時に遅延・欠落するため現実的でない。
  **「後から再タグ付けされた記事」も原理的に一切救えない。**
  なお費用面の副作用は軽微だった（Public リポジトリの Actions は無料枠無制限。
  翻訳結果は `state.translations` にキャッシュされるので **run を増やしても Gemini の
  リクエストは増えない**）。増えるのは feed-bot のコミット数と Pages デプロイ回数だけ。
- **LGTM 数（`likes_count`）で絞り込んで質を担保する** — ⚠️ **この用途では原理的に機能しない。**
  **新着記事の LGTM は必ず 0 から始まる**ので、`likes_count > 0` で絞ると**投稿直後の記事が
  構造的に全部除外される**。実測でも**新着20件のうち18件が LGTM 0**（経過14.7時間の記事でも 0）。
  集約は投稿から数時間以内に走るため、フィルタとして成立しない。
  「数日後に再評価して後から入れる」なら理屈は通るが、**タイムラインが数日遅れて並ぶ**うえ
  再評価の状態管理が必要になり、得るものに見合わない。
- **タグや文言で「初心者向け」記事を除外する** — ⚠️ **却下。取りこぼしとして報告された記事
  そのものが `Security` / `新卒エンジニア` / `初心者向け` タグの入門記事だったため、
  除外すると要望と矛盾する。**
  **項目11（HackRead）でノイズを許容したのとは事情が違う。** あちらで許容したのは
  **セキュリティと無関係な記事**（SEO 記事・`CyberNewswire` の PR 転載）が混ざること。
  こちらは**セキュリティの話であり、質が違うだけで対象内**。
  ＝ **「無関係かどうか」と「レベルが高いかどうか」を混同しない。**
- **Qiita のアクセストークンを最初から使う（1000回/時）** — 認証なしの60回/時で足りている
  （1 run あたり2回）ので、**秘密を増やす理由がない**（項目6）。
  レート制限に恒常的に当たったときの選択肢として残す。
- **`per_page: 100`（API 上限）にする** — 1リクエスト 2.8MB になる（RSS は 3KB だった）。
  **cron 6時間に対して2日分あれば十分な余裕**なので、Qiita 側への負荷を抑えて
  security=50（1.3MB）/ 認証=20（0.8MB）にした。
- **RSS を削除する** — フォールバック先が無くなる。**残しておけば API が使えなくなっても
  「現状より悪くならない」**。ただし RSS に落ちると取りこぼしが再発するので、
  **発動をログと末尾の警告の両方に出す**ようにした（下記）。

**⚠️ 有効性の監視が必要な決定**:

- **API が使えず RSS に落ち続けても、run は緑のまま静かに 4件/run に戻る。**
  これは Qiita で 47% を失っていた元の状態そのもの。そのため
  **`[qiita] ⚠️ RSS フォールバック発動: <理由>` をログに出し、末尾の
  `⚠️ N 件のソースでエラー` にも積む**ようにしてある。**この行が出ていたら放置しない。**
- 特に **CI は共有データセンター IP なので、他の利用者と合算して 60回/時 に当たる可能性が残る**
  （ローカルの家庭用回線では検証できない）。**API 化直後は数 run 分ログを確認する。**

**再検討すべき条件**:

- **Qiita がタグフィードの返却件数を増やしたとき**（RSS に戻せば専用実装を消せる）。
  ⚠️ そのときは**「4件だった」という実測から確認し直す**（過去の調査結果をそのまま信じない）。
- **API のレート制限に恒常的に当たるようになったとき** → アクセストークン（無料・1000回/時）を
  Secrets に追加する。それでも足りないなら `per_page` と取得タグ数を見直す。
- **API v2 が廃止・仕様変更されたとき**（RSS フォールバックが常用になるので、
  そのときは cron 短縮を含めて設計をやり直す）。
- **他ソースでも同じ問題が疑われるとき** — CLAUDE.md の「フィードから何日分遡れるか」の表を見る。
  **BleepingComputer（2.4日分）と HackRead（1.8日分）は余裕が薄い**が、
  どちらもフィード件数を設定では増やせないため、対策は cron 短縮しかない（現状は許容）。
- ⚠️ **Qiita の占有率が上がることは承知の上で受け入れた**（取り込み全体の 25% → 約34%）。
  入門記事も同じ比率で増える。**「探すコストが上がった」と感じたときは、除外ではなく
  上記の使い分け（無関係か / レベルが違うか）から考え直す。**

## 20. Zenn の CDN キャッシュ（最大12時間）は迂回しない

**決定**: Zenn のトピックフィードが CDN で最大12時間キャッシュされ**掲載が最大12時間遅れる**ことを
把握したうえで、**キャッシュバスター（`?_=<run id>` を付けてキャッシュを回避する）を採用しない**。

**理由**:

- **記事の損失は 0%。** フィードは20件（約1.5日分）返すので、12時間の遅延は窓が吸収する。
  実測でも「未取込」だった9件は**すべて直近12時間以内の投稿＝遅延であって損失ではない**。
  ＝ **解決するのは「表示が遅れる」ことだけで、得られるものが小さい。**
- **壊れ方が悪い。** 将来 Zenn 側の実装が変わってクエリパラメータ付き URL が空や
  エラーを返すようになった場合、`aggregate.ts` の graceful degradation が働いて
  **前回キャッシュがそのまま残り、run は緑のまま Zenn だけ静かに止まる**。
  これは CLAUDE.md が繰り返し警告している最悪の失敗パターン（翻訳が 429 で静かに止まった前例、
  X が上流の枯渇で静かに stale 化した前例と同じ形）。**リターンが小さいのにこの形のリスクを
  負うのは釣り合わない。**
- **`s-maxage=43200` はサイト側の意思表示に等しい**（「12時間はキャッシュでよい」）。
  毎回それを迂回するのは行儀が悪い。公開フィードを無償で使わせてもらっている立場と合わない。
- **代わりに「仕様として記録する」を選んだ。** 遅延に気づいたときに調べ直さないよう、
  CLAUDE.md の Zenn の節と `feeds.config.ts` のコメントに実測値付きで書いてある。

**却下した案**:

- **キャッシュバスターを付ける** — 上記のとおり。⚠️ **実装方法は分かっている**:
  `rss.ts` の `toRequestUrl()` にソース単位のフラグを足してクエリを付与する。
  ローカル実行では `GITHUB_RUN_ID` が無いので値の作り方に一手間かかる。
- **cron を短くして遅延を縮める** — キャッシュが12時間効くので**cron を詰めても遅延は縮まらない**
  （同じ古いキャッシュを何度も読むだけ）。効果がない。
- **Zenn の記事一覧 API（`zenn.dev/api/articles`）に切り替える** — 最新順が即座に取れることは
  確認したが、**公開ドキュメントの無い非公式エンドポイント**。項目19 で Qiita API v2 を採ったのは
  **公式にドキュメント化された API** だからで、ここは事情が違う。
  損失 0 の問題に非公式 API 依存を持ち込む理由がない。

**再検討すべき条件**:

- **Zenn の投稿ペースが上がって 20件の窓が1日分を切ったとき**（12時間の遅延を吸収できなくなり、
  **遅延ではなく損失に変わる**）。現在 12.7件/日 なので約1.5日分。
  ⚠️ **20件 ÷ 投稿ペースが 0.5日に近づいたら、この決定は無効。**
- **Zenn が `s-maxage` を短くしたとき / キャッシュをやめたとき**（問題自体が消える）。
- **「掲載が遅い」ことが実際に不満になったとき。** 現状は「損失0なら遅延は許容」という判断。

## 21. 取りこぼした64件の復元と、著者名の混在解消は実施しない

**決定**: Qiita を API 化した時点で残っていた**取りこぼし64件（`2026-07-31` 以降）を復元しない**。
RSS 時代の `author`（フィード名）と API 由来の `@ユーザーID` が**混在する状態も直さない**。
⚠️ **ただし復元手段は実装済みで残してある**（`scripts/backfillQiita.ts` ＋ `npm run backfill:qiita`）。

**理由**:

- **復元しても過去記事がタイムラインの奥に入るだけ。** `publishedAt` は元の投稿日なので
  トップには現れない。**手間とリスク（feed.json を手で書き換えてコミットする）に見合わない。**
- **今は過去記事にアクセスする経路が「その日付までスクロールする」しかない。**
  アーカイブの完全性が価値を持つのは**検索できるとき**で、その前提がまだ無い。
- **著者名の混在は表示の不揃いだけで動作に影響しない。** しかも `retentionMax`（Qiita は
  1000件・14〜23件/日 なので**約50日で入れ替わる**）＝**放っておけば自然に解消する。**
  有限で自動的に消える問題に手を入れる理由がない。
- **重要なのは流出が止まっていること**（項目19 で解決済み。CI で +4/run → +26/run を確認）。
  **過去の穴埋めはそれとは別問題で、優先度が低い。**
- **急ぐ理由がない。** Qiita API はタグの全期間（`tag:security` は 12,827件）を引けるので、
  **後から復元することもできる**（時間が経つと取れなくなる、という性質の作業ではない）。

**却下した案**:

- **今のうちに復元しておく** — 上記のとおり。「いつでもできる」ので先送りのコストがほぼゼロ。
- **著者名だけ揃える** — 混在は約50日で自然解消する。それだけのために `feed.json` を手で
  書き換えてコミットする（＝cron と衝突しうる例外操作）価値がない。
- **`scripts/backfillQiita.ts` も消す** — ⚠️ **却下。** 実装済みであることに加え、
  **設計で踏んだ罠2つ（下記）を再発見するコストが高い**。消すと次に必要になったとき
  同じ調査をやり直すことになる。

**残してある手段（使い方）**:

```bash
npm run backfill:qiita -- --since 2026-07-31                              # 既定は dry-run
npm run backfill:qiita -- --since 2026-07-31 --apply                      # 復元を書き込む
npm run backfill:qiita -- --since 2026-07-31 --normalize-authors --apply  # 著者名を揃える
```

- ⚠️ **`--since` は必須（既定値をあえて設けていない）。「feed.json の最古日」を起点にしてはいけない。**
  API の一覧は created_at の厳密降順ではなく**後からタグを追加された過去記事が混ざる**ため、
  最古が数ヶ月前になっている（実測で `2025-12-25` が入っていた）＝**数千件を流し込む事故になる。**
- ⚠️ **ページ送りの停止条件は「そのページに `--since` 以降の記事が1件も無いこと」。**
  「`--since` より古い記事が1件出たら打ち切る」は**誤り**（同じ理由で1ページ目で止まる）。
  実測で比較済み: **誤った条件では 16件、正しい条件では 64件**を検出した。
- **`--max-add`（既定300）** を超えたら書き込まずに中断する安全弁がある。
- **`--normalize-authors` は復元とは独立したフラグ。** 片方だけ revert したいことがあるので、
  **実行するときはコミットを分ける**（著者名は API を叩かず記事 URL から導出する）。
- **冪等**（id で重複排除）＝ cron と衝突したら **origin 側を採用して再実行すればよい。**
- ⚠️ 実行は `feed.json` を書き換えてコミットする＝
  「動作確認後に `git checkout --` で破棄する」通常ルールの**例外**。
  **cron（6時間ごと）と重ならない時間に実行し、直後に push する。**
- 復元分に**サムネは付かない**（次回の cron で `enrichArticles` が og:image を補完する）。
  日本語記事なので **Gemini の消費は増えない**（`summarizeSources` が空のため。項目5）。

**再検討すべき条件**:

- ★ **検索機能を実装したとき。** これが主たる条件。**過去記事を検索する用途が生まれると
  アーカイブの完全性の価値が上がる**ので、そのときに `--since 2026-07-31`（API 化以前の穴）で
  復元する。
- **「あの記事が無い」と実際に困ったとき。**
- **`retentionMax` を大きく伸ばして長期アーカイブに寄せたとき**（項目14）。
  保持を伸ばすほど「穴が空いたまま長く残る」ことになる。
- ⚠️ **著者名の混在については、約50日を過ぎたら自然解消しているので再検討そのものが不要になる。**
  それでも混在が残っているなら、`retentionMax` の想定（14〜23件/日）が崩れているということ
  ＝そちらを調べる。

## 22. HackRead の 403 に対して何もしない（無効化も回避も調査もしない）

**決定**: HackRead のフィードが `Status code 403` を返して取得できなくなったが、
**`disabled: true` にせず、回避も追加調査もしない。** そのまま失敗させ続ける。

> **観測された事実（記録の正確さのために区別する）**: 403 は**ローカル実行で観測**した
> （前日は**同じ UA で 10 件取得できていた**）。**CI でも起きているかは run ログを見ておらず未確認。**
> `Cloudflare 配下だがフィードは UA を問わず 200` という `feeds.config.ts` のコメントは
> **この観測と矛盾している**（当時は事実だった）。

**理由**:

- **Cloudflare の設定変動なので自然復旧の可能性がある。** 前日は取得できていた＝
  こちら側の変更が原因ではない。**待てば直るものに手を入れると、直ったことに気づけなくなる。**
- **実害が限定的。** 過去28件は保持されており（全ソース共通の蓄積設計）、
  **他ソースは正常**。1ソースが落ちても run は成功する（graceful degradation）。
- **回避策（UA の詐称など）は確実性が低く、かつ筋が悪い。** これは項目20（Zenn のキャッシュ
  バスターを見送った判断）と**同じ論点**＝**相手が拒否しているものを迂回する**行為になる。
  Cloudflare のボット判定を騙しに行くのは、公開フィードを無償で使わせてもらっている立場と合わない。
- **仮に回避できても、別の判断が残る。** HackRead は **PR配信・SEO記事のノイズ**を承知で採用した
  ソース（項目11）で、その要否は**まだ判断していない**。
  ＝ **回避に労力を割いても、その先に「そもそも入れ続けるか」という未決の問題がある。**
- **`disabled: true` にしない理由**: 停止させると**復旧しても自動では戻らない**
  （`SOURCES` 配列との二重管理も発生する）。**そのままにしておけば毎 run 試行し、
  復旧した瞬間に取得が再開する。**

**却下した案**:

- **`disabled: true` にする** — 上記のとおり復旧を自動で拾えなくなる。
  また `feeds.config.ts` の `disabled` と `src/lib/feed.ts` の `SOURCES` の両方を戻す必要がある
  （CLAUDE.md「無効化したソースを復活させるとき」）＝**一時的な障害に対して重い操作。**
- **UA を変えて回避を試みる** — 確実性が低く、上記のとおり迂回そのものが方針に合わない。
  仮に通っても Cloudflare 側の変更で再び落ちる（＝いたちごっこ）。
- **ソースごと削除する** — 403 が一時的である可能性が高い段階で、実装・型・色・
  ドキュメントを消すのは早い。ノイズを理由に外す判断をするなら、
  **それは項目11 の議論として行う**（403 とは別の理由で決めるべきこと）。
- **CI の run ログを取得して原因を詰める** — 現時点では**分かっても打ち手がない**
  （相手側の設定なので）。復旧しないと判断した段階で調べればよい。

**どうやって気づくか**（放置する決定なので、これが要）:

- **`disabled` にしていないので、失敗すれば毎 run の末尾に
  `⚠️ N 件のソースでエラー: - hackread: ... Status code 403` が出続ける。**
  逆に**この行が消えたら復旧した合図。**
- 取得件数の推移でも分かる（`git show origin/main:src/data/feed.json | jq '[.items[]|select(.source=="hackread")]|length'` が 28 のまま動かない）。

**再検討すべき条件**:

- **数週間経っても 403 が続き、過去28件が古くなりすぎたとき。**
  ＝ タイムラインに古い HackRead 記事だけが残る状態になったら、`disabled` か削除を検討する。
- **403 が解消して取得が再開したとき。** ⚠️ **そのときは PR・SEO記事のノイズ問題
  （項目11 の「1週間ほど運用して除外の要否を判断する」）が改めて必要になる。**
  **403 で止まっていた期間は観測期間に数えられない**＝判断材料が溜まっていない。
- **他のソースでもエラーが出るようになり、hackread のエラーが埋もれて見分けられなくなったとき。**
  ＝ 上記の「気づく仕組み」が機能しなくなるので、そのときは放置をやめる
  （個別に `disabled` にするか、エラー表示の作りを見直す）。

## 23. トップの情報密度を下げる（説明文のソース名列挙を外し、フィルタバーの sticky を外す）

**決定**: ソースが8つに増えて画面上部が長くなったため、**2つの変更を行った**。
① トップの見出し下の説明文から**ソース名の列挙を外し**「公開フィードから自動集約。」にする。
② **フィルタバーの sticky をやめる**（スクロールすると画面外へ流れる）。固定するのはヘッダーだけ。

> ⚠️ **②は一度「折りたたみ機能」として実装したうえで取りやめている**（下記「経緯」）。
> 動機が共通（トップの情報密度を下げる）なので1項目にまとめてあるが、
> **判断も再検討条件も別々**なので下で分けて書く。

### ① 説明文からソース名の列挙を外した

**理由**:

- ソース名を全部並べると
  「Zenn・Qiita・はてなブログ・The Hacker News・Dark Reading・BleepingComputer・The Register・HackRead から自動集約。」
  になり、**h1 より長い説明文**になっていた。ソースは今後も増える見込みなので、放置すると悪化する。
- **h1「セキュリティ情報フィード」が既に「何を」を言っている。** 説明文は
  「**どうやって**（公開フィードから・自動で）」を言うほうが役割が分かれて情報量が増える。
- ソース一覧の情報自体は失われない＝**フッター・about ページ・RSS・OGP 画像に残っている。**

**⚠️ なぜ `sourceListText()` を短くしなかったか（重要）**:

- `sourceListText()` は **5箇所で共有**されている:
  ①トップの説明文 ②`<meta name="description">` ③フッター ④RSS の channel description
  ⑤OGP 画像（`scripts/generateOgImage.ts`）。
- **この関数を短くすると②〜⑤を巻き込む。** 特に②と⑤は
  **検索結果と SNS シェア時に表示される説明文**で、「どのソースを集めているか」が
  そのままサイトの価値の説明になっている＝**ここからソース名が消えるのは損失。**
- そこで **`index.astro` の1行だけを固定文で上書き**した。
  **自動生成の仕組み（項目7）は無傷。**
- ⚠️ **将来「トップにもソース名を出したい」と思ったら、`sourceListText()` を呼び戻すのは
  `index.astro` の1行だけでよい**（関数側は何も変わっていない）。
- ⚠️ 逆に**この固定文を見て「SOURCES から自動生成に戻すべき漏れ」と誤解しないよう、
  `index.astro` にコメントを置いた**（項目7 の方針＝表示テキストは `SOURCES` 由来にする、
  と矛盾して見えるため）。

**却下した案**:

- **何も書かない（更新時刻だけ残す）** — 見出し直下が時刻だけになり、
  初見の人に「自動集約されたフィードである」ことが伝わらない。
- **「セキュリティ情報を自動集約。」** — h1 と「セキュリティ情報」が重複する。
- **「N ソース・M 件を集約。」のように件数を出す** — ⚠️ **却下したが、理由は項目7 とは違う。**
  項目7 が「N ソース」という書き方を禁じているのは**手書きだと更新漏れするから**で、
  `SOURCES.length` から自動生成するなら**取り残されない＝禁止の理由には当たらない**。
  却下したのは単に**トップに件数を出す価値が薄い**（読者の判断を助けない）ため。
  ＝ **項目7 の禁止ルールを破ることになるから却下したのではない。**
  将来件数を出したくなったら、自動生成である限り項目7 とは衝突しない。

**再検討すべき条件**:

- **ソースを大幅に減らしたとき**（3つ程度に戻れば列挙しても短いので、自動生成に戻してよい）。
- **「どのソースを集めているのか、トップで分からない」という不満が出たとき。**
  そのときは列挙を戻すのではなく、**about ページへの導線**を検討するほうが筋が良い
  （about には `SOURCES` から生成した説明付きカードがある）。

### ② フィルタバーの sticky をやめた

**⚠️ 経緯（先に折りたたみを実装し、取りやめた）**:

1. 当初の依頼は「**フィルタを折りたたんで隠せるようにする**」だった。開閉ボタン・`localStorage`
   （`todaysec:filter`）・ちらつき防止のための `<head>` インラインスクリプトまで実装し、
   コミットした（`feat: ソースフィルタと言語トグルを折りたためるようにする`）。
2. そのあと**本来の課題が「スマホで記事の表示領域が狭い」ことだと確認され**、
   その原因が**フィルタバーが sticky で常に画面に居座っていること**だと分かった。
3. ＝ **sticky を外すだけで、ユーザーの操作なしに同じ効果が得られる。**
   折りたたみは revert した（`revert: フィルタの折りたたみ機能を取り消す`）。
4. **教訓: 解こうとしている課題（縦が狭い）と、依頼された手段（折りたたみ）を切り離して
   確認する。** 手段から実装に入ると、より単純な解を見落とす。

**理由**:

- **チップが「すべて＋8ソース」の9個あり、スマホ幅では4行前後に折り返す。**
  sticky にしていると**その高さ（実測 375px 幅で約190px）が常時、記事の表示領域から削られる。**
- **「読みながら頻繁にソースを切り替える」使い方をしていない。** 常時見えている必要がなく、
  切り替えたいときは先頭へ戻ればよい（スクロール量は多いが、頻度が低いので割に合う）。
- **ユーザーの操作が要らない。** 折りたたみは「畳む」という一手間と、
  「畳んだまま絞り込みが残って理由が見えない」という副作用を伴った。sticky を外すだけなら
  **UI が増えないので副作用もない。**
- 付随して**実装が単純になった**: `--stack-h`（ヘッダー＋フィルタ高）が不要になり、
  sticky オフセットの変数は `--header-h` だけになった。`sticky-surface`（背景の不透明化＋
  ぼかし）もフィルタバーには不要になった（背後に何も重ならないため）。
- 日付見出しは**ヘッダーの直下**（`top-[var(--header-h)]`）に貼り付く。

**却下した案**:

- **折りたたみ機能** — 一度実装したが上記のとおり取りやめた。**ユーザー操作が必要**で、
  実装も重い（`localStorage`・ちらつき防止の `<head>` スクリプト・`display: contents`・
  畳んだときの選択中表示）。**sticky を外すだけで同じ目的が達せられるなら、そちらが単純。**
  ⚠️ 実装は `git show` で読める（`feat: ソースフィルタと言語トグルを折りたためるようにする`
  とその revert）。再実装するならそこから復元できる。
- **ヘッダーにフィルタアイコンを置く（押すとメニューで開く）** — 常時アクセスできる利点はあるが、
  **ヘッダーが混み合う**（ロゴ＋FEED/ABOUT/RSS で既に埋まっている）。加えて
  「開く → 選ぶ → 閉じる」の階層が増え、チップを直接押す今の手軽さを失う。
  ソース切り替えの頻度が低い前提と釣り合わない。
- **上スクロールでフィルタを再表示する（hide-on-scroll-down）** — スマホアプリで一般的だが、
  **スクロール量を監視する JS が必要**で、静的サイトに動的な挙動を持ち込む。
  「上に戻る」操作でしか出ないので**結局スクロールが必要**＝先頭に戻るのと大差ない。
  実装コストに対して得るものが小さい。
- **チップを横スクロールの1行にする** — 縦は最小になるが、**隠れたチップに気づけない**
  （9個のうち3〜4個しか見えない）。ソース名を見比べて選ぶ用途に合わない。

**再検討すべき条件**:

- ★ **「読みながら頻繁にソースを切り替えたい」と感じたとき。** これが主たる条件。
  そのときは**折りたたみ**（上記のとおり実装を履歴から復元できる）や
  **ヘッダー常駐**を再検討する。**その場合も「縦が狭い」問題が戻ることを承知の上で決める。**
- **チップの数が減って1〜2行に収まるようになったとき**（sticky にしても縦の負担が小さい）。
- ⚠️ **`SHOW_LANG_FILTER_CHIP` を `true` に戻したとき**（項目9）＝チップが1つ増えて
  折り返しが増えるので、この判断の前提（4行前後）が変わる。
- ⚠️ **カードの `isolate` は今も必須**（項目とは別の話だが関連）。sticky フィルタとの
  ブリードを防ぐために入れたものだが、**sticky な日付見出しとの間で同じ問題が起きる**ので
  外さないこと（CLAUDE.md に記載）。

## 24. CloudNative BLOGs は全体フィードを「セキュリティ」カテゴリで絞って取り込む

**決定**: CloudNative BLOGs（クラウドネイティブ社の技術ブログ）を追加する。
**カテゴリ別フィードが存在しないため、全体フィードを `<category>` で絞り込む**
（`feeds.config.ts` の `cloudnative.filter.includeCategories: ["セキュリティ"]`）。
そのために **`rss.ts` にソース別の絞り込みの仕組みを新設した**。

**理由**:

- **依頼は `blog.cloudnative.co.jp/category/security/`＝「セキュリティカテゴリが欲しい」だった。**
  カテゴリで絞るのは**要望そのものの実現**であり、後付けの制限ではない。
- ⚠️ **カテゴリ別フィードは存在しない**（実測）。`/category/security/feed/` と `/category/security/feed` は
  **HTML のカテゴリページへリダイレクト**、`/category/security/rss`・`/rss.xml`・`/atom.xml` は **404**。
  サイトが `<link rel="alternate">` で示す唯一のフィードが **`/feed.xml`（全体・50件）**。
- **絞らないと目的から外れる記事が7割になる。** 実測のカテゴリ内訳は
  **セキュリティ 32% / SaaS 20% / コラム 16% / AI 14% / その他 18%**。
  「PMが娘のランドセル選びで学んだこと」「フルリモートの入社初日ってどんな感じ？」
  「非エンジニアの新米PMがPMBOKを学んでみた」といった記事が**最多カテゴリを占める**。
  **セキュリティ情報サイトとして目的から外れる。**
- **`<category>` が明示的に付いているので判定が確実**（ヒューリスティックではない）。
  実測で**複数カテゴリを持つ記事は 0件**＝1記事1カテゴリなので照合が単純。
- **絞ったあとの中身は狙いに合っている**（Langflow 脆弱性とシャドー AI 統制、パスキー登録
  ヴィッシング、Entra ID の MFA 廃止、Netskope DLP など）。
- **項目12（The Register）と同じ判断。** あちらは「総合メディアなので**セクション限定の
  正しい解が存在するなら使う**」と決めた。The Register は URL で絞れたが、ここは URL では
  無理でフィード内の `category` で絞れる、という**手段の違いだけ**。
- 取りこぼしリスクも最小＝フィードは50件（約29日分）返し、絞り込み後は 0.55件/日。
  **全ソースで最も余裕がある。**

**⚠️ 項目11（HackRead）との使い分け ——「質が低い」と「話題が違う」は別問題**:

- **項目11 で許容したのは「質が低い」ノイズ**＝ HackRead に混ざる
  「Top 10 Companies to Hire Power BI Developers」のような **SEO 記事**と、
  `dc:creator` が `CyberNewswire` の**プレスリリース転載**。
  これらは**セキュリティの話題ですらない or 広報**で、**除外条件が不確実**（PR かどうかは
  著者名からの推定）。だから「まず観測してから決める」とした。
- **項目24 で絞ったのは「話題が違う」記事**＝ CloudNative の PM・人事・カルチャー・AI 記事。
  **質は高い**が、このサイトの対象範囲の外にある。しかも
  **サイト自身がカテゴリで明示している**＝除外条件が確実。
- ⚠️ **この2つを混同すると判断がぶれる。** 判断の順序は:
  1. **対象範囲の外か（話題が違うか）** → 外なら**絞る**（サイト側が機械可読な目印を
     持っているなら確実に絞れる）
  2. **対象範囲内で質が玉石混交か** → **絞らない**（何を「質が低い」とするかは主観で、
     機械判定すると Qiita の入門記事のような**要望どおりの記事まで落ちる**＝項目19 参照）
- ＝ **「ノイズが多いから絞る」という理由付けはしない。**「対象外だから絞る」が正しい理由。

**却下した案**:

- **A. 全体フィードをそのまま取り込む** — 実装は既存の仕組みだけで済む（`rssUrls` に1本
  足すだけ）が、**1日あたり 1.15件の対象外記事が入る**。タイムラインは時系列で混ざるので、
  読者は毎回それを読み飛ばすことになる。**「件数を増やす」より「探すコストを上げない」**
  （項目3 と同じ優先順位）。
- **B. 見送る** — 絞り込みの仕組みを作れば解決するので、見送る理由がない。
  絞ったあとの記事の質は高く、日本語の一次情報として価値がある。
- **カテゴリページ（HTML）をスクレイピングする** — フィードで足りるので不要。
  HTML 構造の変更で壊れるうえ、`publishedAt` や抜粋の抽出を自作することになる。
- **`dc:creator`（著者）で絞る** — このブログは著者とカテゴリが対応していないので使えない
  （同じ著者がセキュリティとコラムの両方を書く）。
- **除外側（`excludeCategories` / `excludeAuthors`）も今回まとめて作る** — ⚠️ **却下。**
  今回必要なのは「含める」条件だけ。**HackRead の除外は「除外するか自体が未決」**（項目11）で、
  条件が `dc:creator` か `categories` かも決まっていない＝**推測で実装すると、使われないまま
  実態と合わない仕組みが残る**。⚠️ **仕組みは拡張しやすい形にしてある**＝
  `RssItemFilter` にフィールドを1つ増やし、`matchesFilter` に数行足すだけ
  （`dc:creator` で絞るなら `RssItem` への `creator` 取り込みも必要）。

**⚠️ 静かに壊れないための仕掛け**:

- **サイト側が「セキュリティ」というカテゴリ名を変えると 0 件になる。** 絞り込みは
  完全一致で照合するため。これは「run は緑のままソースだけ止まる」という
  このリポジトリで繰り返し起きた失敗パターン（翻訳の 429・X の上流枯渇・項目20 参照）。
- そこで **「フィードは件数を返したのに絞り込みで全件落ちた」場合を検出し、
  `⚠️ 絞り込みで全件除外された` として警告＋末尾のエラー集約に積む**ようにした。
  **実際に存在しないカテゴリ名を設定して発火を確認済み。**
- あわせて**通常時も「フィード 50 件中 34 件を絞り込みで除外」をログに出す**＝
  条件が意図どおり効いているかを後から確認できる。

**再検討すべき条件**:

- **サイトがカテゴリ別フィードを提供したとき**（絞り込みをやめて URL で限定できる＝
  項目12 と同じ形にできる）。⚠️ そのときは**「404 だった」という実測から確認し直すこと。**
- **カテゴリ名が変わったとき / カテゴリ体系が再編されたとき**（上記の警告で気づく）。
  「セキュリティ」以外にも対象にすべきカテゴリが増えたら配列に足す。
- **`SaaS` カテゴリも対象に入れたくなったとき。** 実測では Intune・Netskope・Keeper・
  認証基盤選定など**セキュリティ運用に近い記事が多く**、境界は微妙だった。
