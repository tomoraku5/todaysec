## 1. フォーク元 `satory074/todayai` をベースにした

**決定**: ゼロから作らず、AI 情報集約サイト `satory074/todayai` をベースに、セキュリティ情報向けへ
改造する形で構築する。**作者の許諾は取得済み。**

**理由**:

- 運用者は開発未経験。「RSS を集めて時系列で並べる静的サイト」に必要な部品
  （集約パイプライン・OGP 補完・保持ポリシー・CI・Pages デプロイ）が既に動く状態で揃っており、
  **学習の出発点として実物が動いていることの価値が大きい**。
- ソースの差し替えが設計上想定されている（`feeds.config.ts` ＋ `SOURCES` 配列の中心レジストリ）ため、
  「AI → セキュリティ」の付け替えが構造変更なしで済む見込みだった。実際そのとおりだった。
- 費用 0 円という制約を最初から満たしていた（公開 RSS ＋ GitHub Pages）。

**却下した案**:

- **ゼロから自作** — 学習効果は高いが、動くまでの距離が遠い。CI・デプロイ・OGP 解決のような
  「本題ではないが必須」の部分で止まるリスクが高いと判断した。
- **GitHub の fork 機能を使う** — 採用せず、コードをベースにした独立リポジトリにした。
  fork のままだと本家への PR が既定動作になり、無関係な改造履歴を持つリポジトリとして扱いにくい。

**再検討すべき条件**:

- 本家の設計（集約→マージ→トリム→補完の2フェーズ構成）が、セキュリティ用途の要求と
  合わなくなったとき。現状は合っている。
- **フォーク元由来の残骸が見つかったとき**は再検討ではなく単純に修正する。URL・アカウント名の
  ハードコードが複数あった（CLAUDE.md「フォーク元からの変更点」表）。同種のものは同じ方針で直す。
- ⚠️ `docs/gcs-storage-setup.md` には**フォーク元の GCP プロジェクト名・バケット名が残っている**。
  これは「使っていない手順書」として意図的に残しているもので、流用するなら自分の環境で作り直す。

## 2. 4ソースを削除し、X だけ温存した

**決定**: `hatena`（はてなブックマーク）/ `layerx` / `workspace`（Google Workspace Updates）/
`gcloud`（Google Cloud リリースノート）を**コードごと削除**。`x` は削除せず
**`disabled: true` で温存**する。

> ⚠️ **依頼時の記憶と実際の履歴に食い違いがあったので、履歴側に合わせて書いている。**
> 「X / LayerX / GCP / Workspace を削除」ではなく、**削除された4つ目は `hatena`（はてなブックマーク）**
> で、**X は削除していない**（`0e43fa2 refactor: 使わない4ソース（hatena/layerx/workspace/gcloud）を削除`、
> および `1d23902 chore: X / LayerX / translate を無効化`）。X は最初に無効化され、その後の
> 削除対象からは外れた、という順序。

**理由**:

- 削除した4つは**セキュリティ用途に内容が合わない**（Workspace/gcloud はクラウド製品の更新情報、
  layerx は AI ニュースレター、hatena はテック全般の人気エントリー）。
  無効化して残すと、`feeds.config.ts` と `SOURCES` の対応を読むたびに「これは何だったか」を
  考えるコストが毎回かかる。
- **layerx / workspace / gcloud は運用コストも高かった**（Gmail OAuth のリフレッシュトークン失効、
  FeedBurner への 302、1エントリ＝1日の専用パーサ）。セキュリティ用途で使わないものに
  この保守を抱える理由がない。
- **X だけ温存したのは、無効化の理由が「内容が合わない」ではないから。** X の停止理由は
  ①既定の取得先がフォーク元作者の公開ブックマーク JSON で、自分のデータではない
  ②外部アカウント取得は X API 有料 — の2点であり、**セキュリティ情報の収集手段としては今も有効**。
  取得先さえ差し替えれば使える状態を残しておく価値がある。
- 削除したものも**要点だけは CLAUDE.md に残し、削除前コミット `c5c9547` を添えた**。
  「はてブ人気エントリーは今人気の約30件しか返さない → 前回分を土台に蓄積する設計が必須」という
  知見は、**今も全ソース共通の仕組みとして生きている**（この設計の由来が分からなくなるのを防ぐ）。

**却下した案**:

- **4ソースも `disabled: true` で温存** — 温存はタダではない。型・設定・専用スクリプト・
  `.env.example`・CI の env が残り続け、読む人が「有効か無効か」を毎回判定することになる。
  復活可能性が実質ゼロのものは消したほうが読める。
- **X も削除** — 上記のとおり停止理由が違うので却下。
- **X の取得先を自分のアカウントに差し替えて有効化** — X API が有料のため費用 0 円の方針に反する。
  無効のまま温存が現実的。

**再検討すべき条件**:

- **X**: 無料または十分安価にセキュリティ関連アカウントのポストを取れる経路ができたとき。
  復活させるときは `disabled: false` だけでは画面に出ない（CLAUDE.md「無効化したソースを
  復活させるとき」の4手順が必要）。
- **削除した4つ**: 復活はまず無い。仮に必要になっても `c5c9547` から実装を読み直せる。
- **温存している `x` のコードが改修の足かせになったとき**（型やパイプラインの変更のたびに
  無効なコードの面倒を見る負担が無視できなくなったら）、温存をやめて削除に倒す。

## 3. はてなブログはタグ横断をあきらめ、個別ブログを列挙する

**決定**: 「セキュリティタグの新着を全ブログ横断で取る」フィードの利用を断念し、
**セキュリティ専門の個別ブログ3本の Atom を列挙**する（`feeds.config.ts` の `hatenablog.rssUrls`）。

**理由**:

- **横断フィードが存在しないことを実アクセスで確認した。** `hatenablog.com/tag/<tag>` は
  `hatena.blog/tag/<tag>` へ 301 したうえで **404**。`/feed`・`?mode=rss`・`.rss`・`/tags/`・
  `/topic/`・`/g/`・`blog.hatena.ne.jp/-/search` もすべて 404（詳細は CLAUDE.md「ソース別の要点」）。
  **推測ではなく実測の結果として無い**。
- 個別列挙は**質が担保できる**という副次的な利点がある。piyolog / Fox on Security /
  GMO Flatt Security はいずれもセキュリティ専門で、横断タグより S/N が高い。
- 増やすのが簡単（`rssUrls` 配列に足すだけ。`limit` は 1 URL あたりなので既存分が痩せない）。

**却下した案**:

- **はてなブックマークの検索 RSS（`b.hatena.ne.jp/q/<word>?mode=rss`）で代替** — 唯一横断で取れる
  経路だが、これは**ブログ記事ではなくブックマーク**＝削除した `hatena` 枠と同じもの。
  「はてなブログ」ソースの中身がブックマークになるのは筋が悪い。
  ただし**ブログ候補を探す用途には有効**（セキュリティ関連語で引いてはてなブログ系ホストを集計する）。
- **網羅性を優先して一般的なはてなブログを広く入れる** — ノイズが増える。当時は
  「件数を増やすより探すコストを上げない」を優先していた（この優先順位は後に項目11で見直している）。

**再検討すべき条件**:

- **はてな側が横断タグフィードを提供したとき。** ⚠️ そのときは
  **CLAUDE.md に記録した「404 だった」という事実から確認し直すこと**（過去の調査結果を
  そのまま信じない）。
- 個別ブログが更新停止・移転したとき。列挙方式は**ブログが死んでも気づけない**のが弱点で、
  ソース別件数が 0 のまま続いていないかを時々見る必要がある。
- 列挙するブログが増えすぎて管理しきれなくなったとき（10本を超えるなら方式を考え直す）。

## 4. Astro 5 → 7 のアップグレードを後回しにする

**決定**: `astro ^5.1.0` のまま据え置く。報告されている脆弱性8件を個別に評価し、
**このサイトには該当しない**と判断した。

**理由**:

- **8件のうち7件は、使っていない機能の脆弱性**だった: `define:vars` / spread props /
  View Transition / Server island / SSR エラーページ。
  **`src/` を実際に検索して不使用を確認済み**（`define:vars`・`{...spread}`・
  `ViewTransitions`/`ClientRouter`/`transition:`・`server:defer` いずれも 0 件。
  `astro.config.mjs` に adapter が無く `output` 指定も無い＝純粋な SSG で SSR エラーページも存在しない）。
- **残る1件（esbuild の開発サーバー）だけが該当**。ただし影響するのは
  **`npm run dev` を実行している間だけ**で、ビルド成果物にも公開サイトにも影響しない。
  **静的サイトなので露出面が構造的に小さい**（実行時にサーバーが存在しない）。
- 対して**メジャーバージョン2つ分の移行はコストとリスクが大きい**。運用者は開発未経験で、
  ビルドが壊れたときの復旧が難しい。**利得（該当しない脆弱性の解消）に見合わない**。
- 代わりに**運用でリスクを潰した**: 「dev サーバーを確認後に必ず停止する」を
  CLAUDE.md の標準ルールに明記（過去に複数ポートに溜まる問題が実際に起きたため）。

**却下した案**:

- **すぐ astro 7 へ上げる** — 上記のとおりコスト過大。
- **`npm audit fix --force` で強制解決** — メジャー更新が無警告で入り、壊れ方が読めない。
  なお通常の `npm audit fix` は実施済み（`98ad263`、12件→3件）。
- **dev サーバーを使わない運用にする** — 表示確認ができなくなり、実害のほうが大きい。

**再検討すべき条件**（⚠️ **この項目は前提が最も崩れやすい**）:

- **使っていないとされた機能を使い始めたとき。** 具体的には:
  - `set:html` を使うコンポーネントを追加したとき（**現在 0 件**。RSS 本文の HTML をそのまま
    描画したくなった場面で踏みやすい）
  - **spread props（`{...props}`）を使うコンポーネントを追加したとき**（現在 0 件。
    共通コンポーネントを抽象化すると自然に出てくる書き方）
  - View Transition（`ClientRouter`）を入れたくなったとき
  - `define:vars` でサーバー側の値をインラインスクリプトへ渡したくなったとき
- **SSR / Server island を有効化したとき**（adapter を入れて `output` を変えたとき）。
  静的サイトという前提が崩れるので、**この項目の判断は丸ごと無効になる**。
- 新たに報告された脆弱性が**ビルド時または成果物に影響するもの**だったとき。
  「dev サーバーのみ」でなくなった時点で評価をやり直す。
- astro 5 のセキュリティサポートが終了したとき。

## 5. Gemini は3行要約に使わず、翻訳だけに使う

**決定**: `translate` は有効（`disabled: false`）だが、**`summarizeSources` は空**のままにする。
＝**非日本語の記事だけ翻訳し、要約はしない。**

**理由**:

- **トークン消費が約16倍違う。** 要約は**記事本文 7,000〜10,000 字**が入力になるのに対し、
  翻訳は**タイトル＋抜粋の約 500 字**。無料枠で回すという前提では差が大きすぎる。
- **日本語ソースは `isJapanese()` でスキップされ、そもそも API を呼ばない。**
  一方 `summarizeSources` に入れると**原文の言語を問わず要約対象**になる＝
  **日本語記事にまで API を使うことになる**（Zenn/Qiita/はてなブログが全部対象になる）。
  「英語ソースだけ 1日4〜6リクエスト」という費用感が崩れる。
- 解きたかった問題は「**英語の見出しが読めない**」であって「日本語記事が長い」ではない。
  翻訳だけで問題は解ける。

**却下した案**:

- **記事系ソースを `summarizeSources` に入れて3行要約する** — 上記のトークン量に加え、
  **要約は誤りが混入したときに気づきにくい**（翻訳は原文と1対1で照合できるが、
  要約は「書いていないこと」が混ざっても検出しにくい）。個人の学習目的のサイトで
  AI 生成の要約を一次情報のように見せるのは避けたい。
- **翻訳ごと無効にする（原文のまま並べる）** — 英語ソースが増えて新着の約8割が英語になり、
  見出しだけで取捨選択できない状態になったため却下。

**再検討すべき条件**:

- **無料枠の条件が変わったとき**（拡大すれば要約を試す余地が出る。縮小すれば翻訳自体を見直す）。
- **抜粋が短すぎるソースが主力になったとき。** Dark Reading の抜粋は 69〜219 字（中央 148 字）＝
  ほぼ1文しかなく、翻訳しても内容が分からない。こういうソースが増えるなら、
  **`enrichArticles` が取る記事本文を使った要約**に価値が出る。
- ⚠️ **`summarizeSources` を変えるときは `aggregate.ts` の `ENRICH_VERSION` を必ず上げる**
  （上げないと翻訳済みキャッシュが再生成されず、変更が反映されない）。
- 翻訳が出なくなったときは方針の問題ではなく **Gemini の HTTP 4xx を疑う**
  （モデル提供終了で 429 になった前例あり。CI は緑のまま静かに壊れる。CLAUDE.md 参照）。

## 6. API キーはローカル `.env` に置かず、GitHub Secrets のみに置く

**決定**: `GEMINI_API_KEY` は GitHub Secrets にのみ設定する。**ローカルの `.env` には置かない。**

**理由**:

- **このリポジトリは Public。** 誤コミットが即座に公開される。
- **「置かなければ漏れない」という構造的な排除**を選んだ。`.gitignore` や
  コミット前チェックは**運用者の注意力に依存する**が、そもそもローカルに秘密が存在しなければ
  誤コミットは原理的に起こらない。運用者は開発未経験で、注意力に頼る対策は破綻しやすい。
- **実害がない。** ローカルで必要なのは表示確認（`npm run dev`）であり、これは
  コミット済みの `src/data/feed.json` があれば動く。**翻訳は CI で走れば十分**。
- ローカルで翻訳が走らない＝`titleJa` が付かないだけで、`state.translations` から
  再適用されるので**データが壊れることもない**（graceful degradation）。

**却下した案**:

- **`.env` に置いて `.gitignore` で守る** — 一般的なやり方だが、上記のとおり注意力依存。
  Public リポジトリでの事故のコスト（キーの失効・再発行）に見合わない。
- **キーを環境変数として都度エクスポートする** — 漏洩リスクは下がるが手順が煩雑で、
  そこまでしてローカルで翻訳を走らせる必要がない。

**再検討すべき条件**:

- **リポジトリを Private にしたとき**（前提そのものが変わる）。
- **ローカルで翻訳の挙動を検証する必要が出たとき**（プロンプトの調整など）。
  そのときも「常設せず、検証中だけ環境変数で渡し、終わったら消す」を優先する。
- ⚠️ **`.env` / `.env.example` は依頼者の権限設定で書き込みが拒否される。**
  変更が必要なら手作業で対応する（CLAUDE.md の標準ルール「触ってはいけないもの」）。

## 7. 説明文・フィルタ・about を `SOURCES` から自動生成する

**決定**: ソース一覧を表示するすべての箇所（トップの説明文・フッター・`<meta description>`・
フィルタチップ・about ページ・RSS の description）を、`src/lib/feed.ts` の `SOURCES` 配列から
生成する（`661d10d refactor: ソース一覧の表記を SOURCES から自動生成する`）。

**理由**:

- **手動更新の漏れが実際に発生した。** はてなブログを追加したとき、コードは全部直したのに
  **README と説明文が「Zenn と Qiita から集約」のまま残った**。
  同じ情報が複数箇所に散っていると、ソースを足すたびに全部を思い出す必要がある。
- ソースの追加は**このサイトで最も頻度の高い作業**。1回の追加で直す箇所が多いほど漏れる。
- `SOURCES` は既に「今どのソースを集めているか」の中心レジストリになっていた＝
  **新しい仕組みを作るのではなく、既にある単一の真実を参照させるだけ**で済んだ。

**却下した案**:

- **手動のまま、チェックリストで漏れを防ぐ** — チェックリストは作ったが、それだけでは不足。
  **自動化できるものは自動化し、チェックリストは自動化できないものに集中させる**ほうが機能する
  （現に CLAUDE.md のチェックリストは「自動で追従するもの」と
  「手で更新が必要なもの ★ここが漏れやすい」を明確に分けている）。

**再検討すべき条件**:

- ソースごとに**説明文を個別に出し分けたくなったとき**（自動生成は一律の書式になる）。
  そのときも `SOURCES` にフィールドを足す方向で解決し、表示側にベタ書きしない。
- ⚠️ **README.md / CLAUDE.md / OGP 画像は自動追従しない。** ここは今も手作業で、
  実際に漏れる場所。CLAUDE.md のチェックリスト「3. 手で更新が必要なもの」を必ず通す。

## 8. 言語トグルは削除せず、条件付き表示にする

**決定**: 「日本語 / 原文」トグルを、翻訳データが1件も無いときは描画しない
（`hasAnyTranslation(items)` が true のときだけ出す。`c43c3b0`）。

**理由**:

- 翻訳を無効にしていた時期、トグルは**押しても何も起きない飾り**になっていた。
  機能しない UI は「壊れている」という印象を与える。
- **削除すると、翻訳を有効化したときに作り直しになる。** 翻訳は温存する方針だったので、
  復活が前提だった。
- 条件付き表示なら**翻訳を有効化した瞬間に自動で復活する**＝
  「有効化したのにトグルが出ない」という第二の事故が起きない。
  実際、翻訳を有効化したとき（`e29e520`）にトグル側の作業は不要だった。

**却下した案**:

- **トグルを削除する** — 上記のとおり作り直しになる。
- **無効状態でも常に表示する** — 押しても何も起きない UI が残る。
- **フラグで手動制御する** — 項目9と違い、ここは**データを見れば自動判定できる**
  （翻訳が存在するかどうか）。判定できるものを人間の設定に落とすと、
  設定と実態がズレる余地を作ることになる。

**再検討すべき条件**:

- 翻訳を**恒久的にやめると決めたとき**（そのときは実装ごと削除してよい）。
- ⚠️ **`isTranslated` / `hasAnyTranslation` はこのトグル専用ではない。**
  `BilingualText` の表示判定にも使われているので、消すときは巻き込みを確認する。

## 9. 「日本語」フィルタは、追加したあと使ってみて非表示にした

**決定**: 「日本語」フィルタチップを追加した（`06ad4d1`）が、実際に使ってみて不要と判断し、
**削除ではなく `SHOW_LANG_FILTER_CHIP = false` で表示だけ止めた**（`d719f29`）。

**理由**:

- 追加した動機は正しかった（英語ソースが増え、新着の約8割が英語になり日本語記事が埋没する）。
  しかし**使ってみると、実際にはそのフィルタを押さなかった**。翻訳が有効で日本語の見出しが
  付いているため、埋没の体感がそれほど無かった。
- **「作ってから使ってみないと分からない判断だった」ことを記録しておきたい。**
  机上では必要に見えたが、実運用では不要だった。
- **削除せずフラグにしたのは、前提が季節変動するから。** 蓄積が進んで英語記事の比率が
  さらに上がれば、また必要になりうる。**作り直しを避けたい。**
- **フラグで止めても副作用がない**ことを確認済み: フィルタ JS はチップの `data-filter-kind` を
  見るだけで「日本語」チップの存在を前提にしていない。またフィルタの選択状態は
  `localStorage` に保存していない＝**「日本語」を選んだ状態で再訪して壊れる経路が存在しない**。

**却下した案**:

- **削除する** — 上記のとおり復活の可能性があり、判定ロジック（`isTranslated`）と
  記事側の目印（`data-orig-lang`）も含めて消すと復元コストが高い。
- **そのまま表示し続ける** — 押さないチップがフィルタ列を占有する。フィルタは
  `flex-wrap` で行数が変わるため、不要なチップは**レイアウトにも影響する**。
- **項目8と同じく自動判定にする** — できない。「翻訳データがあるか」は判定できるが
  「このフィルタが有用か」は判定できない。**人間の判断が必要なのでフラグが妥当**。

**再検討すべき条件**:

- **日本語記事の埋没が体感できるようになったとき**（英語ソースをさらに増やしたとき、
  日本語ソースの更新が止まったとき）。`true` に戻すだけで復活する。
- 翻訳を無効化したとき（英語のまま並ぶので埋没が一気に顕在化する）。

## 10. バッジ色はグループ配色にせず、個別色を続ける

**決定**: ソースが増えて色差の基準を満たせなくなったが、**グループ配色（国内/海外で色を共有）へは
移行せず、ソースごとに個別色を割り当て続ける**。

**理由**:

- かつての合格基準は「**既存どうしの最小色差 ΔE 58.3（Qiita↔ロゴ）を上回る**」で、
  7色目までは満たせた。しかし **8色目 The Register で ΔE 48.3、9色目 HackRead で 47.4** と
  **2回連続で基準未達**。
- **これは努力で解決できない。** 色相環は 360° しかなく、白背景で AA 4.5:1 を満たす明度帯も限られる。
  明度・彩度を動かして全色相を総当たりしても**上限は 48 前後**だった。
  ＝**基準のほうが維持不能**であり、基準を守るために設計を変えるのは本末転倒。
- **バッジには常に「ソース名の文字」が入る。** 色は判別の**主役ではなく補助的な手がかり**だと
  割り切れば、ΔE が下がっても実用上の問題は小さい。
- 個別色をやめると**「どのソースか」を色で大まかに掴む手がかりが完全に失われる**
  （グループ配色では The Hacker News と Dark Reading が同色になる）。得るものより失うものが大きい。

**却下した案**:

- **グループ配色（国内/海外メディアで数色を共有）** — 基準は満たせるが上記のとおり情報量が落ちる。
  ⚠️ ただし**移行方法は分かっている**: `SourceMeta` に `group` を足して `badgeClass` を
  グループ由来にするだけ（`SOURCES` 駆動の自動追従はそのまま使える）。方針を変えるときのために記録。
- **基準を満たすまで色を探し続ける** — 総当たりで不可能と確認済み。
- **基準を下げて「達成」したことにする** — 数字を都合よく動かすと基準が意味を失う。
  **未達は未達として記録し、そのうえで続ける**と決めた（各色のコメントに
  「何色目で・どの色と・どれだけ近いか」を残している）。

**再検討すべき条件**:

- **ソースがさらに増えて、色が実用上まったく区別できなくなったとき。**
  目安として ΔE が 40 を切るあたり、または**運用者自身が色で見分けられないと感じたとき**。
  そのときはグループ配色へ移行する（上記の移行方法）。
- **バッジからソース名の文字を消す変更をしたとき** — この判断の前提（文字があるから色は補助）が
  崩れる。**そのときは色が唯一の手がかりになるので、この決定は無効**。
- ダークテーマを追加したとき（白背景前提のコントラスト計算をやり直す必要がある）。

## 11. HackRead は一度見送ったあと、ノイズを承知で採用した

**決定**: 調査時に一度**見送った** HackRead を、方針を変えて**採用**した。
**除外の仕組みは意図的に作っていない。**

**理由**:

- **一度見送った理由**: ノイズが多い。取得10件のうち**セキュリティ報道は4件程度**で、
  残りは「Top 10 Companies to Hire Power BI Developers in 2026」のような
  **セキュリティ無関係の SEO 記事**と、`dc:creator` が `CyberNewswire` の**プレスリリース転載**。
  当時は「件数を増やす」より「探すコストを上げない」を優先していた。
- **採用に転じた理由**: **除外が本当に必要か、どの条件が適切かは、机上では決められない**と考え直した。
  1週間ほど運用して実態を見てから判断するほうが確実。**ノイズを含んだまま入れて様子を見る。**
- **除外を先に作らなかったのは、作ると判断材料が消えるから。** 除外条件を入れた状態で運用すると
  「除外しなければどうだったか」が分からなくなる。**まず観測し、それから決める。**
- 項目3で採った「件数より S/N」という優先順位を、ここでは**意図的に逆にしている**。
  この不一致は認識したうえでの選択（HackRead は速報性があり、S/N の低さと引き換えに得るものがある）。

**却下した案**:

- **見送ったまま採用しない** — 判断材料が得られない。
- **除外条件を実装してから採用する** — 上記のとおり観測を潰す。加えて
  「ソースごとの除外条件」の仕組みを `rss.ts` に持たせる必要があり、**別作業**の規模になる。

**再検討すべき条件**（⚠️ **これは「いつか」ではなく「近いうちに必ず」再検討する項目**）:

- **1週間ほど運用したら、実態を見て除外の要否を判断する。** これが採用の前提条件。
  **判断せずに放置すると、「ノイズを承知で採用した」が「ノイズに慣れた」に変わる。**
- 除外すると決めたときの実装候補は2つ（どちらも `rss.ts` にソースごとの除外条件を持たせる仕組みが必要）:
  1. `dc:creator` が `CyberNewswire` のものを除外（PR記事はこれでほぼ落ちる）
  2. `categories` による除外（フィードが categories を持つので技術的に可能）
- ノイズ比率が悪化したとき、または**除外の仕組みを作るコストが見合わないと判断したとき**は
  ソースごと外す選択肢もある。
- ⚠️ フィードは10件（約3日分）しか返さない＝**CI が数日止まると取りこぼす**。
  BleepingComputer（約2日分）と並んでリスクが高い部類。

## 12. The Register はセキュリティセクション限定フィードを使う

**決定**: 全体フィードではなく **`/security/headlines.atom`（セクション限定）** を使う。
かつ設定ファイルには**リダイレクト前の「人が読める URL」を書く**。

**理由**:

- The Register は**総合 IT メディア**で、クラウド・ハードウェア・企業ニュース・宇宙開発まで扱う。
  全体フィード（`/headlines.atom`）ではセキュリティ以外が大量に混ざる＝
  **このサイトの目的（セキュリティ情報）に合わない**。
- セクション限定フィードは**実測 50 件すべてがセキュリティ関連**だった（タイトル全件を目視確認）。
- **人が読める URL を書くのは、転送先が壊れやすいから。** 実際には
  `api.theregister.com/api/v1/article?...&query=tag:security` へリダイレクトするが、
  この URL は `site_id=2` / `remapper=rss` といった**内部パラメータを含む**。
  サイト側の都合で変わったときに、内部 URL を直書きしていると原因が分かりにくい。
- ⚠️ **The Hacker News とは逆の判断をしている。** あちらは最終 URL（FeedBurner）を直接書いた。
  **転送先が安定した公開エンドポイントかどうかで使い分けている**（FeedBurner は公開サービス、
  The Register の api.theregister.com は内部 API）。この使い分けは意識的なもの。

**却下した案**:

- **全体フィードを使って件数を稼ぐ** — 目的に合わない記事が主になる。
  項目11（HackRead）でノイズを許容したのとは事情が違い、こちらは**セクション限定という
  正しい解が存在する**（ノイズを避ける手段があるのに使わない理由がない）。
- **最終 URL（`api.theregister.com/...`）を直接書く** — リダイレクトを1回減らせるが、
  内部パラメータへの依存が増える。

**再検討すべき条件**:

- **セクションフィードの内容が変質したとき**（セキュリティ以外が混ざり始めたら、
  全件目視の再確認をやり直す）。
- **`/security/headlines.atom` が 404 になったとき。** ⚠️ 他の形
  （`/security/feed/`・`/security/rss`・`/security/atom.xml`・`/security/index.atom`）は
  **すべて 404 と確認済み**なので、そこを試し直すのは無駄。同内容を返すのは
  `/security/headlines.rss` のみ。
- リダイレクト先が変わって取得が不安定になったとき（そのときは最終 URL 直書きを再評価する）。

## 13. `feed.json` は git 保管のままにし、GCS モードへ移行しない

**決定**: `feed.json` を `src/data/feed.json` として git にコミットする運用を続ける。
**GCS 保管モードは実装が存在するが有効化しない**（リポジトリ変数 `GCS_BUCKET` 未設定）。

**理由**:

- **費用 0 円という方針が最優先。** GCS は料金が発生しうる。
- git 保管なら**履歴がそのまま追える**し、壊れたときに `git show` で過去の状態を取り出せる。
  開発未経験の運用者にとって、**確認手段が git だけで完結する**のは大きい。
- 手順書（`docs/gcs-storage-setup.md`）は**フォーク元の GCP 設定のまま**で、
  そのままでは動かない＝移行には実質的な作り直しが必要。

**却下した案**:

- **GCS へ移行する** — 6時間ごとのコミットループが消える（履歴が feed の更新で埋まらない）
  という明確な利点があるが、費用とセットアップコストが方針に合わない。

**再検討すべき条件**:

- **リポジトリサイズが実用上の問題になったとき**（`feed.json` は蓄積し続ける設計で、
  6時間ごとに全文がコミットされる＝履歴が単調に増える）。
- コミット履歴が `chore: update feed` で埋まって**人間の変更が追えなくなったとき**。
- ⚠️ 移行するなら手順書の GCP プロジェクト名・バケット名を**自分の環境で作り直す**こと。

## 14. 年齢による削除をやめ、ソース別の件数上限にした

**決定**: 「N 日より古いものを消す」（旧 `maxAgeDays`）を**廃止**し、
**ソースごとの件数上限 `retentionMax`** を唯一の上限にする。

**理由**:

- **ソース別の枠にしないと、物量の多いソースが他を押し出す。** 全体で一律の上限だと、
  1日10件の The Hacker News が、週数件のはてなブログを押し流してしまう。
- 年齢での削除は**「古いが価値のある記事」を機械的に捨てる**。セキュリティ情報は
  数ヶ月前のインシデント記事にも参照価値がある。
- 全ソースが「前回分を土台に蓄積する」設計になっているため、
  **取得窓が狭い RSS でも過去分が失われない**という利点を、年齢削除が打ち消していた。

**却下した案**:

- **全体で一律の件数上限** — 上記のとおりソース間で不公平になる。
- **上限なし（無限に蓄積）** — `feed.json` が肥大しビルド時間と git 履歴に響く。

**再検討すべき条件**:

- `feed.json` のサイズがビルド時間や表示速度に影響し始めたとき。
- **ソースごとの投稿頻度が大きく変わったとき**（`retentionMax` は頻度から逆算した値。
  既定 1000 は約10件/日なら3ヶ月分という見積もり）。

## 15. ロゴの色だけ専用変数に分離した

**決定**: ロゴをエメラルドグリーン `#0f9b6c` に変更する際、
**サイト全体のアクセント色（コバルト `#2f5fff`）は変えず**、`--color-logo` 系の専用変数を新設した。

**理由**:

- `--color-accent` は**フィルタチップ・言語トグル・カード hover が共有している**。
  ロゴを変えるつもりで触ると**サイト全体が巻き込まれる**。
- 「ロゴだけ変えたい」という意図を**変数の構造として表現しておく**ことで、
  次に触る人（＝将来の自分）が事故らない。

**却下した案**:

- **`--color-accent` を直接変更する** — サイト全体が緑になる。意図と違う。
- **ロゴにハードコードで色を書く** — 変数管理から外れ、変更箇所が追えなくなる。

**再検討すべき条件**:

- **サイト全体の配色を刷新すると決めたとき**（そのときは分離の意味が薄れる）。
- ⚠️ Tailwind v4 は**実際に使われている `@theme` 変数しか CSS に出力しない**ので、
  `--color-logo-bright` / `-deep` は定義済みでもビルド後の CSS には現れない。**不具合ではない。**

## 16. アクセス解析は Cloudflare Web Analytics を使う

**決定**: Cloudflare Web Analytics（Cookie 不要）を使い、**トークン未設定でも動く**形にする。

**理由**:

- **Cookie を使わない**＝同意バナーが要らない。個人の学習目的のサイトに同意管理を持ち込みたくない。
- **トークンは公開値**（ページソースに出る）なので Secret ではなく**リポジトリ変数**で扱える
  （`PUBLIC_` 接頭辞は Astro/Vite のクライアント露出に必須）。項目6の「秘密を増やさない」方針と整合する。
- **未設定ならタグを出力しないだけ**でビルドは壊れない（graceful）。
  設定しないまま運用を始められる。

**却下した案**:

- **Google Analytics** — Cookie と同意対応が必要。個人サイトには重い。
- **解析を入れない** — 「誰も見ていないのか、見られているのか」が分からないと改善の判断ができない。

**再検討すべき条件**:

- Cloudflare Web Analytics が有料化または終了したとき。
- ページ単位より**詳細な分析が必要になったとき**（現状は必要ない）。

## 17. テストフレームワークを導入しない

**決定**: テストフレームワークを入れない。検証は `npm run typecheck` / `npm run build` と
`npm run aggregate` の実行ログ（ソース別件数）で行う。

**理由**:

- **このサイトのロジックの大半は「外部フィードを取ってきて並べる」**で、
  壊れるとしたら**外部の都合**（フィードの形式変更・404・レート制限）。
  これはユニットテストでは検出できず、**実際に取得してログを見る**しかない。
- **型検査が実質的なテストとして機能している**（`tsconfig` の `include: ["**/*"]` により
  `scripts/` も `astro check` で検査される）。
- 運用者は開発未経験。**テストの保守自体が学習コストになり、本題から逸れる**。

**却下した案**:

- **Vitest 等を入れて主要関数をテストする** — `truncateSafe` や `isJapanese` のような
  純粋関数にはテストが書けるが、**壊れて困っているのはそこではない**。
- **E2E テスト** — 静的サイトで JS も最小限。費用対効果が低い。

**再検討すべき条件**:

- **純粋なロジックが増えたとき**（除外条件の実装＝項目11 は、まさにテストが有効な種類のコード。
  「この記事は除外されるか」は入出力が明確でテストしやすい）。
- **同じ不具合を繰り返すようになったとき**（回帰テストが必要というサイン）。
- ⚠️ **`npm run build` は Astro が import するファイルしか型検査しない。**
  `scripts/` を変更したら**必ず `npm run typecheck` を通す**（現状これが唯一の検査手段）。

## 18. OGP 画像は手で作らず、コードから生成する

**決定**: `public/og-default.png` を `scripts/generateOgImage.ts`（SVG 組み立て → sharp で PNG 化）で
生成する。**手で画像を差し替えない。**

**理由**:

- 手で作った画像は**差分が追えず、作り直せなくなる**。文言やソース一覧が変わるたびに
  「元のデザインファイルはどこか」を探すことになる。
- スクリプトは `SOURCES` を読むので、**ソースを追加しても文言の修正は不要**
  （項目7の自動生成と同じ考え方）。**実行を忘れないことだけが問題**。

**却下した案**:

- **画像編集ソフトで作る** — 上記のとおり再現性がない。
- **ビルド時に毎回生成する** — 生成環境のフォントに依存する（下記）ため、
  ビルドのたびに字形が変わりうる。**生成済み PNG をコミットする**運用にした。

**再検討すべき条件**:

- ⚠️ **sharp は `package.json` の直接依存ではなく astro の推移的依存。**
  将来 astro が落としたら `npm i -D sharp` が必要になる。
- ⚠️ **テキストは生成した PC のフォントでラスタライズされる**（サイトの Web フォントは載らない）。
  **別 PC で再生成すると字形が変わる**ので、通常は再生成しない。
- デザインを大きく変えるとき（そのときもスクリプトを直す。画像を差し替えない）。
